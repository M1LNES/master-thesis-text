\chapter{Úvod}\label{chapter:introduction}
V dnešním světě, kdy se software i díky nástupu umělé inteligence vyvíjí rychleji než kdy dříve, je zajištění kvality a spolehlivosti aplikací klíčovým faktorem 
pro úspěch. Testování hraje zásadní roli při odhalování chyb, zajištění důvěry uživatelů a zvyšování kvality softwaru.
S nástupem velkých jazykových modelů (LLM) se objevují nové příležitosti pro automatizaci generování testů \cite{wang2024softwaretestinglargelanguage}, 
což může výrazně zefektivnit proces testování a snížit náklady spojené s manuálním vytvářením testovacích scénářů. 
Hranice možností se stále posouvají nejen co se týče výkonností jednotlivých modelů (např. známých GPT, Claude) a společností přicházejících na~trh,
ale i co se týče přístupů k využití těchto modelů pro generování testů. I přes tento inovační potenciál je ale třeba myslet na rizika a 
výzvy spojené s rozšířeným využíváním LLM - a to nejen z pohledu softwarového (např. riziko halucinací, nedostatečná kvalita generovaných testů), 
ale i na cenovou a etickou stránku věci (např. náklady na využívání LLM, otázka ochrany dat a soukromí).
\newline

Cílem této diplomové práce je prozkoumat možnosti generování kódu pomocí velkých jazykových modelů v rámci automatizovaného testování a implementovat 
funkční prototyp, který má potenciál výrazně urychlit a zefektivnit proces testování softwaru pomocí end-to-end testů. Aby aplikace byla 
prakticky použitelná, bude zaměřená na generování testů na základě uživatelských příběhů, jež jsou běžně využívány v agilním vývoji softwaru
\cite{10467677} a poskytují přehledný a srozumitelný popis požadavků z pohledu uživatele. To umožní rozšířit možnosti psaní spustitelných 
testů i do oddělení jako je QA (Quality Assurance), které nemusí mít hluboké technické znalosti, ale jsou klíčové pro zajištění kvality softwaru.
Důraz bude kladen na kvalitu vygenerovaných testů, jejich schopnost odhalovat chyby a přínos pro zefektivnění procesu testování.

\chapter{Teoretická část}\label{chapter:therotical_part}
V této kapitole bude představen teoretický rámec nezbytný pro pochopení problematiky autonomního generování testů. 
Z důvodu potřeby transformace obchodních požadavků do funkčního kódu bude nejprve popsáno, jakým způsobem probíhá specifikace v agilním prostředí pomocí uživatelských příběhů 
a akceptačních kritérií. Následně budou rozebrány moderní přístupy k testování softwaru, existující frameworky pro webovou automatizaci a výzvy spojené s testováním v agilním prostředí.

Důležitou částí kapitoly je rozbor velkých jazykových modelů (LLM), které v současnosti slouží jako nástroj pro interpretaci požadavků a generování kódu. 
Budou vysvětleny jejich základní principy, technické parametry a limity spojené s psaním testovacích skriptů. V závěru kapitoly pak budou představeny autonomní agentní systémy, 
které propojují svět testování a umělé inteligence skrze pokročilé architektury a komunikační protokoly. Tento ucelený přehled metodik a technologií poslouží jako základ pro následný praktický 
návrh vlastního řešení.
\section{Agilní vývoj a specifikace požadavků}

IT je jedním z nejrychleji se rozvíjejících odvětví, a to nejen z pohledu technologií,
ale i přístupu k vývoji softwaru. Jak \cite{articleFromWaterfallToAgile} uvádí, tento aspekt vedl k vývoji metodik (např. 
agilní metodiky či vodopádový model), které navrhují řízení v závislosti na vlastnostech produktu, organizačních strukturách či dynamickém prostředí.
Tradiční konzervativnější vodopádový model (populární např. ve stavebnictví) se zaměřuje na důkladné plánování \cite{senarath2021waterfall} a znalost 
požadavků před zahájením vývoje \cite{almeida2017challenges}. V rychle se měnícím prostředí je ale tento přístup často neefektivní,
protože požadavky ze strany uživatelů se mohou rychle měnit a není možné je znát všechny předem. Tento problém řeší agilní metodiky,
které kladou důraz na flexibilitu - díky tomu, že fungují na tzv. iterativním principu (software se vyvíjí v krátkých cyklech často
přezdívaných jako sprinty), umožňují průběžné přizpůsobování se měnícím se požadavkům a rychlejší dodávání funkčních verzí softwaru \cite{almeida2017challenges}. 

Nejznámějším a současně nejrozšířenějším přístupem k agilnímu vývoji je Scrum. Scrum tým se zpravidla skládá z následujících rolí 
\cite{senarath2021waterfall, sassa2023scrum,hron2018scrum, sachdeva2016scrum}:

\begin{itemize}
    \item \textbf{Vývojáři (Developers)} - jsou zodpovědní za vývoj softwaru a implementaci požadovaných funkcionalit (\texttt{features}).
    
    \item \textbf{Scrum Master} - zajišťuje dodržování Scrum procesů, podporuje tým při práci a pomáhá odstraňovat překážky, které by mohly bránit efektivnímu vývoji.
    
\item \textbf{Product Owner} - je zodpovědný za správu produktového backlogu, komunikaci s vývojovým týmem a zainteresovanými stranami (stakeholdery) 
a za zajištění toho, aby vývoj směřoval k naplnění potřeb zákazníka.
\end{itemize}

Hlavní náplní práce Product Ownera je správa backlogu a příprava uživatelských příběhů (často známý pod rozšířejnějším anglickým pojmem \textit{user stories}), 
které specifikují požadované funkcionality z pohledu uživatele \cite{sachdeva2016scrum}.

\begin{figure}[H]
\centering
\includegraphics[width=1\textwidth]{pictures/Scrum-process-flow-1.png}
\caption{Vizualizace Scrum procesu a jeho klíčových fází \cite{faniran2017adopting}.}
\label{fig:scrum_process}
\end{figure}

Vzájemná interakce těchto rolí a posloupnost jednotlivých aktivit je znázorněna na obrázku \ref{fig:scrum_process}. 
Celý proces probíhá v iterativních cyklech (tzv. sprintech), které zpravidla trvají 2-4 týdny
(na zmiňovaném schématu je pro ilustraci uvedena historicky tradiční délka 30 dnů). Během nich 
tým postupuje od výběru prioritních požadavků zákazníka z produktového backlogu (\textit{Product Backlog}), 
přes vytvoření menšího backlogu pro daný sprint (\textit{Sprint Backlog}), až po samotnou implementaci,
která je prokládána každodenními krátkými (15-minutovými) schůzkami. 
Klíčovým výstupem každého sprintu je funkční přírůstek softwaru a zpětná vazba od zákazníka.
A právě uživatelské příběhy tvoří základní pilíř pro specifikování těchto přírůstků.


\subsection{Uživatelské příběhy}
User story je nejpoužívanějším artefaktem v agilním vývoji \cite{9393933userstories} - jedná se o krátký, semi-strukturovaný 
popis požadavků napsán v přirozeném jazyce. Na ukázce \ref{lst:user-story-template} je uvedena standardní šablona, 
podle níž se uživatelské příběhy píší \cite{9393933userstories,9771182userStories, 9325670userStories}.
\begin{center}
\begin{minipage}{0.8\textwidth}
\begin{lstlisting}[
    language=UserStory, 
    lineskip=3pt, 
    caption={Standardní šablona uživatelského příběhu.}, 
    label={lst:user-story-template}
]
As a <type of user / persona>
I want <to perform some action / goal>
So that <some value / benefit is achieved>
\end{lstlisting}
\end{minipage}
\end{center}

Každá user story by měla být napsána z pohledu konkrétního uživatele (\texttt{persona}), s jasně stanoveným cílem (\texttt{goal}) 
a dosaženou hodnotou (\texttt{value}). Hodnota je dosažena pouze tehdy, pokud byl plánovaný cíl úspěšně splněn \cite{9325670userStories}.

Kvalita napsaných user stories je klíčová nejen pro porozumění vývojářů při implementaci, ale také pro následné testování a ověření, že plánovaný 
cíl byl skutečně dosažen. Jednou z metod, která pomáhá jasně definovat kritéria pro úspěšné splnění user story, je \texttt{INVEST} \cite{lucassen2016useinvest}. 
V tabulce \ref{tab:invest_principy} jsou uvedeny jednotlivé principy \texttt{INVEST}, které by měly být dodržovány pro psaní kvalitních uživatelských příběhů.

\begin{table}[H]
\centering
\begin{tabular}{|l|p{10cm}|}
\hline
\textbf{Princip} & \textbf{Popis} \\ \hline
\textbf{Independent} & User story by měla být co nejvíce nezávislá na ostatních stories. \\ \hline
\textbf{Negotiable} & Požadavky by měly být otevřené pro diskusi a případné úpravy. \\ \hline
\textbf{Valuable} & Splnění user story musí přinést jasnou hodnotu koncovému uživateli. \\ \hline
\textbf{Estimable} & Musí být možné odhadnout náročnost implementace (např. čas nebo potřebné zdroje). \\ \hline
\textbf{Small} & User story by měla být dostatečně malá, aby bylo možné ji dokončit během jednoho sprintu. \\ \hline
\textbf{Testable} & Musí obsahovat definovaná akceptační kritéria, podle kterých lze ověřit splnění požadavku. \\ \hline
\end{tabular}

\end{table}

\subsection{Akceptační kritéria}
Zatímco user story charakterizují potřeby zákazníka, akceptační kritéria (často označována zkratkou \texttt{ACC} z anglického \texttt{Acceptance Criteria}) 
jasně popisují \texttt{Definition of Done} (zkráceně \texttt{DoD}) pro konkrétní user story \cite{li2024simac} co je nutno dodržet a udělat, aby byla user
 story považována za splněnou. Týkají se zejména funkcionality (tlačítko dělá to co má), kvalitativních charakteristik 
 (systém reaguje do X milisekund) a obchodní logiky \cite{ferreira2022towards}. 

 Akceptační kritéria mohou být zapsána různou formou - ať už prostý seznam, kde každý bod představuje právě jedno kritérium, 
 nebo formou scénářů, které jsou popisovány pomocí jazyka Gherkin. Tento způsob testování (kdy jsou nejprve napsány testovací 
 scénáře v přirozeném jazyce a následně se implementují samotné testy) se nazývá \texttt{Behavior-Driven Development} (\texttt{BDD}) \cite{9825769gherkin}.
 
\begin{lstlisting}[language=Gherkin, caption={\protect\centering Ukázka testovacího scénáře zapsaného pomocí klíčových slov jazyka Gherkin.}, label={lst:gherkin-example}]
Feature: User Login

  Scenario: Successful login with valid credentials
    Given the user is on the "/login" page
    When the user enters "user@example.com" into the email field
    And the user enters "password123" into the password field
    And the user clicks the "Login" button
    Then the user should be redirected to the "/dashboard" page
    And a welcome message "Welcome back" should be displayed
\end{lstlisting}

Hlavní motivací pro využití Gherkin scénářů je vysoká abstrakce - scénáře jsou psány v přirozeném jazyce (jak je vidět na ukázce \ref{lst:gherkin-example}), což umožňuje 
jednodušší komunikaci mezi technicky zdatnými i netechnickými členy týmu a zároveň poskytují jasný popis požadavků a očekávaného chování \cite{alshammari2025use}.

Pro prostý seznam akceptačních je důležité, aby používal jasný a konzistentní jazyk a zaměřoval se hlavně na testovatelnost, nikoliv na formát zápisu \cite{ferreira2022towards}.
Ukázka takového seznamu je uvedena na ukázce \ref{lst:list-ac-example} - každý bod by měl být jasně identifikovatelný a obsahuje jedno kritérium, které lze ověřit.

\begin{center}
\begin{minipage}{\textwidth}
\begin{lstlisting}[
    language=AcceptanceCriteria, 
    lineskip=2pt, 
    caption={\protect\centering Ukázka akceptačních kritérií zapsaných formou strukturovaného seznamu.}, 
    label={lst:list-ac-example},
    moredelim={[is][\bfseries]{|}{|}} 
]
|Acceptance Criteria for US_01: User Login|

- ac_01 (Success): System grants access to the dashboard when valid credentials (email and password) are provided.
- ac_02 (Success): Navigation to the login page is possible via the "Sign In" button on the landing page.
- ac_03 (Failure): System displays an error message "Invalid credentials" if the password does not match the stored hash.
- ac_04 (Failure): Account is temporarily locked after five consecutive failed login attempts.
- ac_05 (Robustness): Input fields prevent the submission of SQL injection patterns or excessively long strings.
\end{lstlisting}
\end{minipage}
\end{center}

V praxi bývají akceptační kritéria (spolu s uživatelskými příběhy) nejčastěji obsažena v \texttt{ALM} nástrojích (\texttt{Application Lifecycle Management}) 
jako jsou \texttt{Jira}, \texttt{Azure DevOps}, \texttt{Rally} či \texttt{GitHub Projects}. Tyto nástroje nevyžadují specifický formát zápisu, ale umožňují flexibilitu - ať už jde o prostý seznam, Gherkin scénáře nebo 
kombinaci obojího. Např. studie \textit{From bugs to benefits: Improving user stories by leveraging crowd knowledge with cruise-ac} \cite{schwedt2025bugs} zaměřená na generování akceptačních testů vycházela z běžných user stories a jejich 
textových popisů, z něhož následně generovala Gherkin scénáře, z nichž až poté byly implementovány automatizované testy.

\section{Automatizované testování softwaru}
Softwarové testování lze definovat jako hledání chyb či chybějících požadavků v softwaru \cite{7814898swtesting}. Dá se na něj 
nahlížet i z pohledu snižování rizika, což vede v posílení důvěry uživatelů a zlepšení kvality softwaru. Jak také \textit{Software Testing Techniques: A Literature Review} \cite{7814898swtesting} uvádí,
testování je důležitou součástí \texttt{QA} - čím dříve jsou chyby odhaleny, tím levnější je jejich oprava. Testování lze rozdělit 
do několika tříd, jež jsou znázorněny v tabulce \ref{tab:druhy_testu}, která vychází z knihy \cite{herout_testovani_programatory}.

\begin{table}[H]
\centering
\begin{tabular}{|l|p{10cm}|}
\hline
\textbf{Název testu} & \textbf{Popis} \\ \hline
\textbf{Testování podle scénářů} & Tester dle předpřipravených scénářů manuálně prochází aplikaci a kontroluje očekávané chování jednotlivých testovacích kroků. \\ \hline
\textbf{Průzkumné testování} & Tester bez předem známých scénářů prozkoumává aplikaci a hledá chyby. \\ \hline
\textbf{Regresní testy} & Ověřují, zda nově přidané featury nerozbily existující funkce. \\ \hline
\textbf{Jednotkové (unit) testy} & Automatizované skripty, které izolovaně ověřují funkčnost nejmenších částí zdrojového kódu (funkce, metody). \\ \hline

Jednotkové testy jsou nejvíce izolované, píšou se rychleji, a tudíž jsou i levnější. Naproti tomu \texttt{UI} testy 
(\texttt{User Interface} - testy uživatelského rozhraní - např. end-to-end) vyžadují
větší integraci a jejich vývoj je zpravidla dražší (testy se píšou déle a déle běží). Přestože jsou end-to-end testy dražší, 
představují nedílnou součást celé automatizace - bez těchto testů není zaručeno, že komponenty/moduly systému spolu správně 
komunikují a dávají tak koncovému uživateli očekávaný stav.

Při psaní testů se objevují speciální případy testů - a to testy chybně napsané či nestabilní testy. Jedná se o následující 
termíny \cite{herout_testovani_programatory}:

\begin{itemize}
    \item \textbf{Falešně pozitivní (False Positive)} - Test, který selže, přestože testovaná funkcionalita funguje správně.
    
    \item \textbf{Falešně negativní (False Negative)} - Test, který projde, i když testovaná funkcionalita nefunguje správně.
    \item \textbf{Křehké (Fragile)} - Test, který selže kvůli změně v implementaci, přestože testovaná funkcionalita zůstala nezměněna (např. změna názvu HTML elementu).
    \item \textbf{Nestabilní (Flaky)} - Test, který se chová nedeterministicky - může selhat nebo projít bez jakýchkoliv změn v kódu, 
    což ztěžuje identifikaci skutečných problémů (např. problémy se síťovou komunikací).
    
\end{itemize}

Těmto problémům se při psaní testů snaží vývojáři předcházet - a to např. důrazem na determinismus testů, kontrolou správnosti testovaného chování na Code Review nebo využíváním nástrojů 
pro správu testů, které pomáhají identifikovat a řešit nestabilní testy.


\subsection{E2E testování}

End-to-end testování (zkráceně \texttt{E2E}) je typ testování, který ověřuje kompletní funkčnost systému z pohledu koncového uživatele. 
Využívá se přístupu tzv. metody \texttt{black-box} (černé skříňky), kdy tester nemá přístup k implementaci či struktuře systému, 
ale testuje systém jako jeden celek \cite{herout_testovani_programatory, leotta2016approaches}. V případě webových aplikací je možné nahlížet  
na způsoby tvorby end-to-end testů dvěma způsoby \cite{leotta2016approaches}:

\begin{itemize}
    \item \textbf{Capture-Replay} - Tester nejdříve manuálně prochází aplikaci, zaznamenává své akce a následně se tyto akce převedou na automatizovaný skript.
    \item \textbf{Programmable Web Testing} - Testy se rovnou píšou jako zdrojový kód, který využívá frameworky pro webovou automatizaci.
\end{itemize}

Hlavní výhodou přístupu \texttt{Capture-Replay} je rychlost - testy lze vytvořit velmi rychle, nevýhodou je ale nízká kvalita a nestabilita testů, které jsou často náchylné 
k falešně negativním výsledkům (např. když se HTML elementy změní, program funguje stále správně, ale test selže).

Obě tyto perspektivy potřebují lokalizovat a interagovat s HTML elementy. Interakce s HTML elementy lze rozdělit do tří kategorií \cite{leotta2016approaches}:

\begin{itemize}
    \item \textbf{Coordinate-based} - Využívání [X,Y] souřadnic pro interakci s elementy.
    \item \textbf{DOM-based} - Využití \texttt{Document Object Modelu} (\texttt{DOM})/HTML struktury.
    \item \textbf{Vizuální} - Využití rozpoznání obrazu pro určení elementů na obrazovce.
\end{itemize}

Zatímco první kategorie je označována jako zastaralá \cite{leotta2016approaches}, DOM-based přístup je náchylný na drobné změny v HTML struktuře, 
které mohou způsobit selhání testů a vyžadují častou údržbu. Vizuální přístup sice dokáže testovat to, co uživatel skutečně vidí, 
ale je náchylný na změny v rozložení stránky a režie spojená s rozpoznáváním obrazu může být vysoká. Právě snaha o řešení těchto problémů 
vedla k zrodu mnoha testovacích frameworků pro webovou automatizaci, které se snaží zjednodušit a zefektivnit tvorbu end-to-end testů.


\subsection{Přehled frameworků pro webovou automatizaci}
V oblasti webové automatizace existuje velké množství frameworků, které se navzájem liší svými vlastnostmi, podporovanými jazyky a přístupy k testování.
Zde je uveden přehled těch nejpopulárnějších a nejčastěji používaných,

\subsubsection*{Selenium (WebDriver)}
Jeden z nejrozšířenějších a nejstarších nástrojů. Podporuje širokou škálu jazyků (Java, Python, C\#, JavaScript) a prohlížečů prostřednictvím WebDriveru \cite{selenium_docs}. Díky rozšířené 
komunitě, množství dostupných zdrojů a existujících knihoven je Selenium stále velmi populární volbou. Nevýhodou je 
složitější prvotní konfigurace a manuální správa testů, která může (při nesprávném použití) vést k nestabilním testům.

\subsubsection*{Robot Framework}
Open-source framework založený na Pythonu, který využívá klíčová slova pro psaní testů (tzv. \texttt{Keyword-Driven Testing}).
Architektura využívá knihovny SeleniumLibrary pro webovou automatizaci \cite{robot_framework}. Silnou stránkou je jednoduché psaní testů - 
testy jsou psány čitelně v přirozeném jazyce, díky čemuž jim porozumí i netechničtí členové týmu. Se zvyšující se komplexností 
webových aplikací a testů může být nevýhodou nižší flexibilita a nutnost používat externí knihovny pro pokročilé funkce.

\subsubsection*{Playwright}
Moderní testovací framework vyvinutý společností Microsoft. Podporuje více jazyků (JavaScript/TypeScript, Python, Java, .NET) a 
nabízí robustní API (Application Programming Interface) pro interakci s webovými stránkami \cite{playwright_docs}. Výhodou je rychlost testů a podpora pro více prohlížečů (Firefox, WebKit, Chromium) bez 
nutnosti externích driverů. Klíčovou funkcí je také \texttt{Auto-waiting}, který pomáhá eliminovat křehkost testů. Nevýhodou je menší komunita a méně dostupných zdrojů,
jelikož se jedná o relativně nový nástroj.

\subsubsection*{Cypress}
Nástroj zaměřený na testování moderních webových aplikací, který podporuje pouze JavaScript a TypeScript. Běží přímo v prohlížeči \cite{cypress_docs}, což 
urychluje vývoj testů a jejich případné debuggování. Disponuje také funkcí \texttt{Time Travel}, která umožňuje procházet test krok po kroku a vidět stav aplikace v každém kroku. 
Nevýhodou je omezená podpora napříč jazyky, prohlížeči a testování vícero tabů.


\subsection{Výzvy automatizace v agilním prostředí}

Studie \textit{A conceptual model supporting decision-making for test automation in Agile-based Software Development} \cite{butt2023conceptual} identifikovala několik klíčových výzev, které
se vyskytují při implementaci automatizace testů v agilním prostředí. 

\subsubsection*{Údržba a technický dluh}
Jak vyplývá ze zmíněné studie, tento proces je časově náročný a náchylný k chybám. S rostoucím počtem uživatelských příběhů se manuální tvorba 
test casů (testovacích případů) stává bottleneckem, což může vést k následnému nárůstu technického dluhu, kdy se testy stávají zastaralými a všechny 
scénáře nemusí být pokryty, což zvyšuje riziko chyb. 


\subsubsection*{Regresní testování}
Jelikož agilní vývoj vyžaduje rychlé a časté změny, je klíčové zajistit, aby po každé z nich bylo co nejdříve ověřeno na regresních testech, 
že nedošlo k narušení stávající funkcionality. Tento problém je možno částečně řešit automatickým generováním testů přímo z požadavků, aby se 
minimalizoval čas mezi implementací a testováním.

\subsubsection*{Rozdíl mezi specifikací a kódem}
Tato výzva souvisí s jasností požadavků na produkt. Jelikož jsou požadavky napsány v přirozeném jazyce, může docházet k nedorozuměním či nejasnostem,
které mohou vést k nesprávné implementaci či chybám. To má poté za následek:

\begin{itemize}
    \item Nestabilní testovací orákulum - pokud mechanismus pro ověření výsledků není stabilní a předvídatelný, může docházet k velkému množství falešně pozitivních nálezů či křehkým testům.
    \item Náklady na opravu - opakovaná reimplementace funkcionalit vynucuje souběžnou údržbu testů, což výrazně snižuje návratnost (ROI) investic.
    \item Nízká testovatelnost - zaměření na testovatelnost od prvotních fází vývoje výrazně zvyšuje efektivitu automatizace.
\end{itemize}

\section{Velké jazykové modely ve vývoji softwaru}
Velké jazykové modely jsou rozsáhlé, předtrénované, statistické modely založené na neuronových sítí. 
Jedná se zejména o modely založené na architektuře Transformer, které obsahují miliardy parametrů a jsou trénovány na masivním množství 
textových dat. Díky tomuto objemu parametrů jsou schopni zachytit komplexní vzory a vztahy v jazyce (na základě statistické analýzy) a generovat 
text  \cite{minaee2024large}. Navíc vykazují i tzv. \texttt{emergent abilities} - schopnosti jako je schopnost učit se v kontextu, plnit komplexní 
instrukce či řešit více krokové úlohy.

Evoluce jazykových modelů prošla 4 hlavními generacemi \cite{wang2025history}:

\begin{itemize}
    \item \textbf{Statistické jazykové modely (SLM)} - Vznik v 90. letech 20. století, založené na pravděpodobnostních modelech a n-gramových přístupech.
    \item \textbf{Neuronové jazykové modely (NLM)} - Slova mapovaná na vektory (embeddings), k predikci dalších slov využívány rekurentní neuronové sítě (RNN) a později LSTM (Long Short-Term Memory).
    \item \textbf{Předtrénované jazykové modely (PLM)} - Předtrénované na obrovském množství neoznačeného textu a využití fine-tuningu pro zaměření na konkrétní úlohy.
    \item \textbf{Velké jazykové modely (LLM)} - Současné modely s miliardami parametrů vycházející z PLM, které díky masivnímu nárůstu dat a výpočetnímu výkonu dokáží řešit mnoho úloh bez nutnosti dalšího dolaďování (emergent abilities).
\end{itemize}


Základem architektury Transformer, která byla představena v roce 2017 \cite{vaswani2017attention} a je převratná pro vývoj LLM, je tzv. 
mechanismus \texttt{Self-Attention} - ten umožňuje modelovat vliv každého slova v kontextu věty na ostatní slova, což pomáhá efektivněji zachytit 
a pochopit kontextové vazby.

V rámci architektury Transformer se využívají dva hlavní typy bloků - \texttt{Encoder} a \texttt{Decoder}. Zatímco \texttt{Encoder} bloky se zaměřují na zpracování vstupního textu a 
jejich pochopení, \texttt{Decoder} bloky jsou zaměřené na generování výstupního textu na základě těchto reprezentací \cite{wang2025history}. Na modely se pak 
nahlíží tak, jakou část této architektury využívají:

\begin{itemize}
\item \textbf{Encoder-only} - Modely využívající pouze encoder část architektury. Jsou vhodné zejména pro úlohy zaměřené na porozumění textu, například klasifikaci nebo analýzu sentimentu. Typickým příkladem je BERT.
\item \textbf{Decoder-only} - Modely založené pouze na decoder části, optimalizované pro generování textu. Do této kategorie patří například rodina modelů GPT.
\item \textbf{Encoder-Decoder} - Modely kombinující obě části architektury. Využívají se zejména pro úlohy transformace textu, jako je strojový překlad, sumarizace nebo otázky a odpovědi. Příkladem je model T5.
\end{itemize}

Je nutné podotknout, že i přes své schopnosti a potenciál jsou LLM stále jen nástrojem založené na predikci - nejsou schopné skutečnému porozumění, 
a proto může docházet k jevu zvanému \texttt{halucinace} - okamžik, kdy model generuje věcně nesprávný či nesmyslný text, který ale může působit věrohodně.

\subsubsection*{Tokenizace a zpracování dat}

Přestože reasoning tokeny mohou připomínat lidské uvažování, model po dalším cyklu tuto znalost ztrácí - tyto 
tokeny mu tak slouží jako \texttt{State over Tokens}, kam si odkládá mezivýsledky, aby věděl, jak při dalším kroku pokračovat \cite{levy2025stateReasoning}.

\subsubsection*{Context window}
Kontextové okno definuje maximální počet tokenů, které je model schopen zpracovat v rámci jednoho výpočetního cyklu. 
Zatímco starší generace modelů operovaly v řádu nižších tisíců tokenů, současné modely již zvládají pracovat v řádu nižších milionů. 
Průkopníkem v této oblasti se stala společnost Google, která jako první u svých modelů řady Gemini
\footnote{\href{https://ai.google.dev/gemini-api/docs/long-context}{Dokumentace Google AI}} představila kapacitu přesahující jeden milion tokenů. 
Podobné limity nyní postupně adoptují i další poskytovatelé, jako například Anthropic u modelů Claude v rámci platformy Bedrock
\footnote{\href{https://aws.amazon.com/bedrock/anthropic/}{Dokumentace AWS Bedrock (Anthropic)}}.

\subsubsection*{Temperature}
Parametr využívaný modely k určení míry náhodnosti a diverzity generovaného výstupu \cite{renze2024effect}. Čím nižší je hodnota \texttt{temperature}, tím 
konzervativnější a determinističtější je výstup modelu. S vyššími hodnotami stoupá riziko halucinací, ale model nabízí vyšší míru kreativity. Pro úlohy vyžadující 
přesnost a konzistenci se doporučuje nastavit hodnotu \texttt{temperature} na 0. Některé modely (např. v rámci Azure OpenAI) tento parametr neumožňují konfigurovat, 
protože je pevně definován na úrovni modelu \footnote{\href{https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/reasoning?tabs=csharp\%2Cgpt-5\#not-supported}{Dokumentace Microsoft k Azure OpenAI}}.
\subsubsection*{Tool Calling}
Tool Calling (volání nástrojů) je schopnost modelu autonomně využívat externí aplikace či služby (jako jsou firemní API, vyhledávače...), čímž překonávají svá omezení 
jako jsou např. zastaralé informace. Pro správné použití je nutné zajistit, aby model mohl správně identifikovat záměr uživatele, vybrat vhodný nástroj a
správně nastavit vstupní parametry\cite{shen2024llm}. Tuto schopnost lze modelu naučit buď pomocí fine-tuningu na ukázkových interakcích, nebo technikou \texttt{in-context-learningu},
kdy se do promptu, který se zasílá modelu, vloží definice jednotlivých nástrojů, aby věděl, jak je využívat. Tato vlastnost není podporována u všech modelů, a proto 
je třeba předem zkontrolovat dokumentaci, zda je pro daný model Tool Calling dostupný.


\subsubsection*{Prompt Caching}
Prompt Caching je inovativní technika, jež výrazně zrychluje inferenci modelu a snižuje výpočetní nároky tím, že recykluje interní výpočty modelu \cite{gim2024prompt}. 
Vychází z toho, že uživatelské dotazy obsahují často stejné bloky zpráv (např. systémový prompt, specifikace nástrojů, přiložené dokumenty...), které se mezi
dotazy nemění. Namísto přepočítávání těchto bloků si model ukládá jejich výpočty do mezipaměti a při dalším dotazu, který obsahuje identické bloky, 
si je pouze načte z mezipaměti a spojí, čímž se zkracuje doba zpracování dotazu a to bez jakéhokoliv dopadu na kvalitu finálního výstupu. Tato technika
je podporována zejména u novějších modelů a je nutné zkontrolovat dokumentaci, zda je pro daný model dostupná.

jejichž celkový kontext přesáhne hranici 200 000 tokenů. A ještě větší rozdíly jsou u přístupu ke cachování - zatímco např. OpenAI sází na plnou automatizaci 
a slevy pro krátkodobě identické začátky promptů, Anthropic a Google vyžadují explicitní definici ukládaných bloků, což umožňuje efektivnější a dlouhodobější uchování rozsáhlých dat.

Modely, které jsou veřejnosti dostupné (včetně jejich metadat o nástrojích, kontextových oknech apod.), je možné najít na stránkách \href{https://models.dev/}{models.dev}, 
která tak slouží jako centrální repozitář, který usnadňuje vývojářům výběr a porovnání modelů pro jejich konkrétní potřeby.

\subsection{Limity generování}

Ačkoliv LLM prokazují schopnost psát zdrojové kódy, při generování testů na GUI (Graphical User Interface) narážejí na omezení spojená s 
absencí interaktivity s aktuálním prostředím. Hlavními výzvami jsou:

\begin{itemize}
    \item \textbf{Halucinace} - Jazykové modely si mohou při nedostatku kontextu vymýšlet neexistující elementy/selektory. S tímto chováním 
    se setkal Horínek ve své diplomové práci \cite{HORINEK2024thesis}, kdy se modely snažily použít atribut \texttt{aria}, který ovšem daným frameworkem nebyl vůbec podporován.
    
    \item \textbf{Statický kontext} - Model při generování testu nevidí reálný stav DOMu v čase běhu a nedokáže reagovat na dynamické změny na stránce. Tento problém 
    demonstruje Horínek \cite{HORINEK2024thesis} na případu, kdy model generoval výběr prvku z rozbalovací nabídky, ovšem tyto hodnoty se při každé inicializaci databáze měnily a pevně vygenerované selektory 
    tak v době běhu selhávaly.
    
    \item \textbf{Absence zpětné vazby a zotavení z chyb} - Bez možnosti interakce model nemůže v průběhu testu ověřit, zda jeho předchozí kroky byly úspěšné. 
    Na nutnost řešit tento problém při návrhu nástrojů pro generování GUI testů poukazuje ve své práci Holický \cite{HOLICKY2025thesis}. 
    Pokud je test vygenerován čistě staticky, sebemenší nepřesnost nebo neočekávané chování uživatelského rozhraní vede k selhání celého skriptu. Bez implementace dodatečné zpětné vazby (např. předání chybové hlášky zpět modelu) se systém z takové chyby nedokáže zotavit a test zůstává nevalidní.
    
\end{itemize}

Tyto tři body ukazují, že generovat kód staticky pro moderní proměnlivé aplikace nemusí stačit. Pro překonání těchto limitů 
je potřeba opustit paradigma jednorázového promptu a přijít s řešením, které dokáže s aplikací aktivně interagovat, pozorovat výsledky akcí a následně je verifikovat.
Tímto směrem se ubírají tzv. \textbf{agentní systémy} - systémy, které vidí do DOMu a dokážou dynamicky reagovat.




\section{Agentní systémy a autonomní testování}

\subsection{Definice a charakteristika autonomních agentů}
S narůstající komplexností úloh, které jsou na modely umělé inteligence kladeny, se objevuje potřeba systémů k migraci 
od tradičního jednorázového generování k interaktivním a adaptivním systémům, které dokáží reagovat na dynamické prostředí.
Zatímco standardní neagentní přístup (tzv. \texttt{non-agentic workflow}) funguje na principu, 
který generuje výstup na základě jednorázového uživatelského dotazu a čeká na další lidský pokyn \cite{singh2024enhancing}, agentní systémy představují zásadní změnu paradigmatu.
V agentním pojetí se LLM stává jakýmsi ``mozkem``, jenž proaktivně řídí provádění úkolů, samostatně se rozhoduje o dalším postupu a v případě potřeby 
iterativně reviduje své kroky bez nutnosti neustálých zásahů člověka \cite{singh2024enhancing,ahmadi2025mcp,openai2025_agents_guide}.

Ve své základní podobě se skládá ze tří klíčových komponent \cite{openai2025_agents_guide}:



\begin{itemize}
    \item \textbf{Model} - Konkrétní velký jazykový model, který řídí uvažování, rozhodování a celkovou exekuci workflow agenta.
    \item \textbf{Nástroje (Tools)} - Externí funkce nebo API, jenž agent využívá k interakci s vnějším prostředím.
    \item \textbf{Instrukce (Instructions)} - Explicitní pravidla definující agentovo chování - zmenšují prostor pro nejednoznačnosti což vede k efektivnějšímu chování a minimalizaci halucinací.
\end{itemize}


Pro plné fungování v rámci komplexnějších architektur je často zmiňují i další klíčové aspekty, které pomáhají agentům řešit náročnější úlohy. Mezi ně patří 
paměť (\texttt{Memory}), která umožňuje agentovi uchovávat a využívat informace z předchozích interakcí, a dále plánování (\texttt{Planning}), jež umožňuje 
agentovi dekomponovat složitý problém na sadu menších proveditelných kroků \cite{sarkar2025survey}.


\subsection{Architektura ReAct: Spojení uvažování a jednání}

Vzor ReAct (\texttt{Reasoning and Acting}) je klíčový rámec pro pochopení toho, jak autonomní agenti ``přemýšlejí`` a jednají \cite{ahmadi2025mcp}. 
Tento vzor umožňuje jazykovému modelu krok za krokem uvažovat o problému a konkrétními příkazy spouštět nástroje. Díky tomu 
model (místo klasického přístupu, kdy se vygeneruje celý výstup najednou) běží v cyklu, jenž mu umožní iterativně vytvářet, monitorovat a revidovat své kroky.

Jádrem tohoto vzoru je opakující se smyčka, která se skládá ze tří fází \cite{yan2025general}:

\begin{itemize}
    \item \textbf{Thought (Myšlenka)} - Interní monolog, v němž model analyzuje aktuální stav. Na základě svých předchozích instrukcí a aktuálního kontextu hodnotí, co vidí, jaký by měl být další krok a
    jaké nástroje by měl k jeho dosažení použít.
    \item \textbf{Action (Akce)} - Konkrétní volání toolu, který model na základě předchozí úvahy zvolil.
    \item \textbf{Observation (Pozorování)} - Získání zpětné vazby z prostředí po provedení konkrétní akce - tou může být např. pozměněný stav DOMu, nová URL adresa či chybová hláška.
\end{itemize}

Celý tento proces je zobrazen na obrázku \ref{fig:react}. Ten začíná přijetím vstupu od uživatele a pokračuje do agentovy iterativní smyčky, 
kde se střídají fáze uvažování, jednání a následného pozorování. Celý proces končí v okamžiku, kdy agent v rámci fáze myšlení dospěje k závěru, 
že úloha je splněna a vygeneruje výsledný výstup pro uživatele.

Pro QA a automatizované testy představuje tento vzor zásadní posun - díky explicitním krokům je celý proces generování plně transparentní,
interpretovatelný a auditovatelný. Uživatel přesně vidí úvahu, která agenta vedla k výběru určitého lokátoru, což výrazně usnadňuje ladění a zvyšuje
tak spolehlivost celého systému.


\subsection{Model Context Protocol (MCP)}

Model Context Protocol (MCP), představený firmou \texttt{Anthropic} ke konci roku 2024, je otevřený standard pro interoperabilitu, jehož cílem 
je sjednotit a zjednodušit způsob, jakým se modely umělé inteligence propojují s externími nástroji, systémy a daty.\footnote{\href{https://modelcontextprotocol.io/docs/getting-started/intro}{Oficiální dokumentace MCP}} MCP, 
jenž si vysloužil přezdívku ``USB-C for AI applications``, poskytuje jednotné a standardní rozhraní pro komunikaci - je postaven na 
robustním modelu komunikace Client-Host-Server s využitím formátu JSON-RPC 2.0 \cite{sarkar2025survey}:

\begin{itemize}
    \item \textbf{Client} - Protokolová komponenta zabudována do hostitelské aplikace, která udržuje spojení s jedním konkrétním MCP serverem.
    \item \textbf{Host} - Aplikace, která navazuje komunikaci a interaguje s uživateli.
    \item \textbf{Server} - Samostatný nezávislý proces (běžící lokálně nebo vzdáleně), který zpřístupňuje konkrétní funkce (tooly) - slouží jako obálky kolem externích systémů (API, databáze, CLI nástroje...).
\end{itemize}


Obrázek \ref{fig:mcp} zobrazuje ukázkový ekosystém MCP, v němž hostitelské aplikace - od vývojových prostředí (IDE) jako je Visual Studio Code až po vlastní specializované platformy - 
komunikují se servery pomocí jednotného rozhraní. Díky této architektuře servery fungují jako univerzální adaptéry, překládají požadavky modelu do specifických protokolů (SQL, REST API) 
pro externí služby typu GitHub či Slack, což radikálně zvyšuje modularitu a zjednodušuje integraci nových funkcí do agentních systémů.
\begin{figure}[H]
    \centering
    \includegraphics[width=1\textwidth]{pictures/client.pdf}
    \caption{\protect\centering Ukázková architektura Client-Host-Server v rámci Model Context Protocolu.}
    \label{fig:mcp}
\end{figure}

Zásadní význam MCP pro autonomii agentů spočívá v dynamické správě dostupných nástrojů a dat - agent se skrze protokol MCP dokáže automaticky dotázat serveru na seznam 
dostupných nástrojů a získat k nim přesné definice parametrů. Díky tomu agent v hostitelské aplikaci sám zjistí, jaké nástroje může v rámci své úlohy využívat, 
a to bez nutnosti explicitního předávání těchto informací. 
Tento přístup umožňuje agentům být skutečně autonomními - dokážou se adaptovat na měnící se prostředí a využívat nové nástroje, které se objeví, aniž by bylo potřeba měnit jejich základní instrukce či prompt.

\section{Analýza struktury a sémantiky vstupních artefaktů}
Důležitým faktorem pro úspěšnou automatizaci testů je správné pochopení a zpracování vstupních artefaktů, které jsou základem pro generování testů.
Jak bylo zmíněno v kapitole \ref{chapter:therotical_part}, tyto artefakty mohou mít různou formu - od textových dokumentů (např. uživatelské příběhy, akceptační kritéria) až po strukturované formáty (např. Gherkin).
V ALM nástrojích uživatelské příběhy často nemají jednotnou strukturu, což výrazně ztěžuje jejich zpracování. Zejména nástroje jako \texttt{Jira} nabízejí 
uživatelům velkou flexibilitu (nejen) při správě uživatelských příběhů. K prozkoumání této problematiky lze využít a nahlédnout na 
již existující Jira instance, které jsou přístupné veřejnosti. Zde je několik existujících instancí, ze kterých lze získat 
cenné informace o struktuře a sémantice uživatelských příběhů:

\begin{itemize}
    \item \textbf{Atlassian Jira}\footnote{\url{https://jira.atlassian.com/secure/BrowseProjects.jspa}} - Instance zaměřená na vývoj softwaru samotné společnosti Atlassian (poskytovatel Jira software). Projekty jsou organizovány podle jednotlivých produktů (např. Jira Software, Confluence, Bitbucket...).
    
    \item \textbf{Apache Jira}\footnote{\url{https://issues.apache.org/jira/issues/}} - Instance zaměřená na vývoj open-source softwaru. Projekty jsou organizovány podle jednotlivých open-source projektů (např. Hadoop, Tomcat, Kafka...).
    
    \item \textbf{MongoDB Issue Tracker}\footnote{\url{https://jira.mongodb.org/secure/BrowseProjects.jspa}} - Instance zaměřená na vývoj databázových systémů. Projekty jsou organizovány logicky dle menších celků (např. MCP server, Shell, drivery dle programovacích jazyků...).
    
    \item \textbf{Mojang Studios Bug Tracker}\footnote{\url{https://bugs.mojang.com/}} - Instance zaměřená na vývoj her (Minecraft). Jednotlivé projekty jsou dílčí částí her (např. Java Edition, Bedrock Edition, Launcher...).
\end{itemize}

Před samotnou investigací jednotlivých instancí je vhodné definovat metodiku, jakým způsobem byla data pro analýzu získávána. 
Vzhledem k obrovskému množství ticketů ve veřejných repozitářích nelze spoléhat na manuální procházení. 

Pro průzkum a extrakci relevantních uživatelských příběhů byl využit nativní dotazovací jazyk \textbf{JQL (Jira Query Language)}. 
Tento nástroj umožňuje filtrování napříč projekty na základě mnoha atributů, jako jsou typ úlohy, stav řešení, 
časové okno vytvoření či fulltextové vyhledávání v obsahu ticketu.

Na ukázce \ref{lst:jql-example} je zobrazen dotaz zapsaný v jazyce JQL, který kombinuje několik vlastností:
\begin{itemize}
    \item \textbf{Filtrování dle projektu a typu} - Filtrování ticketů z konkrétního projektu a vyloučení bugů.
    \item \textbf{Validace metadat} - Filtrování ticketů na základě přítomnosti metadat.
    \item \textbf{Časové funkce} - Filtrování ticketů na základě času.
\end{itemize}

Díky těmto dotazům je možné snadno získat relevantní vzorky dat z jakékoliv veřejné instance a 
následně je porovnat napříč ostatními instancemi. 

Zkoumání výše zmíněných veřejných instancí ukázalo, 
že navzdory využití stejného softwarového nástroje se přístup k evidenci požadavků velmi liší. 
Tyto rozdíly jsou dány především doménou projektu, firemní kulturou a zavedenými procesy konkrétní organizace. 

\subsubsection*{Metadata ticketů}
Typ ticketů není nijak omezen. Napříč instancemi se vyskytují různé druhy ticketů, přičemž každý z nich může mít
definovanou svou zcela vlastní strukturu (např. Bug může mít pole pro kroky reprodukce, zatímco User Story pole pro akceptační kritéria).
Nejčastěji používanými typy jsou \textbf{User Story} a \textbf{Bug}. Dále se v rámci instancí vyskytují i další typy jako jsou: 
New Feature, Task, Improvement, Test, Question, Sub-task, RTC (Request to Change), Epic, Dependency, Suggestion, Support Request, Build Failure,
Technical Debt a další. 

Co se týče priorit, opět není žádný jednotný systém - a to i v rámci jedné instance. Například v rámci Apache Jira se 
vyskytují priority jak číselné (P0, P1, P2...), tak i textové (Critical, Major, Minor...). V rámci Atlassian Jira se vyskytují priority pouze textové (Highest, High, Medium, Low).
Někdy dochází i k míchání těchto přístupů - např. v rámci MongoDB Jira se vyskytují priority Major - P3, Minor - P4, Trivial - P5, a další.

K určování rozsahů ticketů se využívají různé metriky - od odhadů v rámci story points až po odhady v rámci časových jednotek (hodiny, dny...). 
Co se týče stavu řešení, i zde není jednotný systém - nejčastější stavy jsou To Do, In Progress, Done, 
ale v rámci instancí se vyskytuje i mnoho dalších stavů - Ready to Commit, Awaiting Feedback, Blocked. Když je ticket uzavřen, 
i zde nastává mnoho různých způsobů, jak se uzavření dokumentuje - Closed, Delivered, Resolved, Rejected, Duplicate, Won't Fix, Cannot Reproduce a další.

\subsubsection*{Description ticketu}
V rámci popisu ticketů je společná jedna věc - celý popisek je jeden velký textový blok, který může obsahovat jakýkoliv obsah - 
od čistého textu, přes tabulky a úryvky kódu. Řádná struktura (As a [role], I want [feature], So that [benefit]) 
se vyskytovala velmi ojediněle - většinou se popis skládal z jednoho odstavce bez jakékoliv struktury či akceptačních kritérií.


\subsubsection*{Akceptační kritéria}
Akceptační kritéria lze v rámci Jira instance definovat jako samostatné pole, ale žádný ze 4 zmiňovaných projektů tuto možnost 
nevyužívá - to může být způsobeno tím, že se jedná o veřejné repozitáře, kde není rozšířená role Product Ownera, který by měl na starosti definici 
akceptačních kritérií. 


\section{Specifikace požadavků na systém}
Na základě předchozí analýzy vstupních artefaktů a teoretických poznatků jsou v této sekci definovány konkrétní požadavky 
na navrhovaný systém. Vzhledem k vysoké různorodosti vstupních dat bude systém navržen tak, aby mohl být aplikován na širokou 
doménu projektů, a to bez nutnosti přizpůsobení pro konkrétní instanci.

\subsection{Vymezení rozsahu generovaných testů}
Systém bude primárně navržen pro generování automatizovaných end-to-end testů s důrazem na ověřování chování uživatelského rozhraní (GUI),
obchodní logiku a vizuální interakci s aplikací. Systém naopak nebude koncipován pro verifikaci 
nefunkčních požadavků, jako jsou výkonnostní testy či bezpečnostní testy. Pokud se v akceptačních kritériích objeví 
nefunkční požadavky, systém bude instruován, aby se zaměřil výhradně na funkční aspekty - měření časových metrik v rámci E2E testování v prohlížeči 
může být velmi závislé na výkonu testovacího prostředí (zařízení, síť), což by mohlo vést k nestabilním testům a falešně pozitivním výsledkům.


\subsection{Funkční požadavky (FR) na systém}
Funkční požadavky definují konkrétní chování, které musí systém vykazovat, aby naplnil potřeby uživatelů. 
Vzhledem k využití velkých jazykových modelů definují nejen samotné vygenerování testů, ale i celý proces - tzv. 
\texttt{agentic workflow}. K určení priorit byla využita metoda MoSCoW (M - Must have, S - Should have, C - Could have, W - Won't have) -
výsledné požadavky jsou uvedeny v tabulce \ref{tab:functional_req}.

\section{Koncepční architektura systému}
\subsection{Doménový model aplikace}
Jak ukázala analýza veřejných instancí ALM nástrojů (viz sekce 3.1), vstupní artefakty napříč projekty a odvětvími postrádají jednotnou strukturu.
Pokud by agent přistupoval přímo k surovým datům z těchto různorodých systémů, byla by extrakce informací velmi nespolehlivá a náročná.
Tento systém proto zavádí vlastní, normalizovaný doménový model, který funguje jako standardizovaná mezivrstva mezi nestrukturovanými daty z externích nástrojů a čistým kontextem,
který bude agentovi předán. Díky tomu bude možné zajistit, že agent bude pracovat s předvídatelným a konzistentním formátem dat, což výrazně zlepší spolehlivost a 
efektivitu generování testů.

Struktura obsahuje tři klíčové entity:

\begin{enumerate}
    \item \textbf{Projekt} - Reprezentuje konkrétní testovanou aplikaci. Obsahuje její základní informace (název, popis, URL).
    \item \textbf{Uživatelský příběh} - Reprezentuje jeden konkrétní ticket. Obsahuje relevantní informace pro generaci testů - název, popis, akceptační kritéria a nepovinný dodatečný kontext (např. odkazy na dokumentaci, konkrétní požadavky na testy...).
    \item \textbf{Vygenerovaný test} - Reprezentuje testovací scénář vygenerovaný agentem. Kromě samotného kódu obsahuje i metadata o generování testu (název, použitý model, množství tokenů, celková cena).
\end{enumerate}

Model je znázorněn na obrázku \ref{fig:domain_model}. Mezi entitami jsou definovány relace - mezi projektem a uživatelským příběhem je relace 1:N - projekt může mít více uživatelských 
příběhů, ale každý uživatelský příběh patří pouze jednomu jedinému projektu. V praxi by se našly i výjimky, kdy by uživatelský příběh mohl být sdílen mezi více projekty (např. společná funkcionalita či separátní projekt pro frontend a backend), 
ale dle dříve zanalyzovaných ticketů (které v drtivé většině případů obsahovaly vazbu pouze na jeden projekt) a pro zjednodušení modelu byla tato možnost vyloučena. 
Relace mezi uživatelským příběhem a vygenerovaným testem je také 1:N - jeden uživatelský příběh může mít více vygenerovaných testů, 
ale každý vygenerovaný test patří pouze jednomu jedinému uživatelskému příběhu.

\begin{figure}[H]
    \centering
    \includegraphics[width=1\textwidth]{pictures/business.pdf}
    \caption{Doménový model systému.}
    \label{fig:domain_model}
\end{figure}

Ostatní prvky identifikované v analýze (např. metadata ticketů) jsou záměrně vynechány, protože pro generování testů nepřináší žádnou přidanou hodnotu a navíc jejich 
zahrnování v agentově kontextu by mohlo vést k zvětšení množství tokenů a tím i nákladů na generování testů. 

\subsection{Distribuce a perzistence dat}
Před samotnou definicí architektury agenta je nejprve nutné rozhodnout, jaký způsob distribuce systému zvolit a jakým způsobem ukládat data.
Původní myšlenkou bylo využít tradiční architekturu s nasazením relační databáze (např. PostgreSQL). Výhodou by bylo, že veškeré testy a uživatelské příběhy by byly uloženy 
centralizovaně v jedné konkrétní databázi, což by umožnilo snadné sdílení a přístup napříč uživateli a vývojovými týmy.
Z tohoto přístupu se nakonec ustoupilo kvůli následujícím důvodům:

\begin{itemize}
    \item \textbf{Ukládání výsledných testů} - Největší úskalí by bylo definování tzv. \texttt{source of truth} pro vygenerované testy.
    Pokud by se testy ukládaly do centrální databáze, vznikla by potřeba synchronizace mezi touto databází a prostředími, kde by se testy pouštěly (např. IDE, CI/CD pipeline).
    Databáze by tak obsahovala veškeré vygenerované testy a bylo by možné trasovat, kdy a kým byly testy vygenerovány, 
    ale zároveň by stejně bylo potřeba testy ukládat do repozitářů, aby bylo možné je spouštět a nakonec by stejně zdrojem pravdy pro testy zůstaly repozitáře.
    \item \textbf{Správa databáze} - S produkčním nasazením by bylo potřeba zajistit správu a údržbu databáze, což by vývojáře odvádělo od hlavního cíle - jednoduché generování testů.
    \item \textbf{Závislost na třetí straně} - Program by byl závislý na další externí službě - k závislosti na dostupnosti LLM modelů by se tak přidala i 
    závislost na dostupnosti a správě databáze. Navíc pokud by aplikace běžela jako samostatná služba, vývojáři by museli z vývojových prostředí otevírat další rozhraní, což 
    by mohlo vést k nižší adopci nástroje.
\end{itemize}

Tato analýza vede k závěru, že tradiční přístup s databází by nedisponoval uživatelskou přívětivostí, která je pro adopci nástroje klíčová.
Všechny výše zmíněné nevýhody řeší tzv. \textit{local-first} přístup, 
který umožňuje vývojářům pracovat s nástrojem přímo z jejich lokálního prostředí bez nutnosti přepínání do jiných rozhraní či závislosti na externích službách.
Systém bude distribuován jako samostatný instalovatelný balíček (prostřednictvím správce balíčků NPM - Node Package Manager), 
který si uživatel pouze nainstaluje do svého projektu, kde chce testy generovat (případně může jednou globálně, pokud chce testy generovat napříč vícero projekty).
Následně jen pomocí jednoduchého CLI příkazu spustí systém lokálně a celý proces generování testů proběhne přímo na jeho zařízení. Jediné nastavení, které bude muset provést, 
je konfigurace přístupových údajů k LLM modelům, což bude záležitost několika řádků v konfiguračním souboru, který bude umístěn lokálně v projektu.

Díky tomu budou mít vývojáři systém přímo ve svém IDE bez nutnosti otevírání dalších rozhraní, \texttt{source of truth} bude přímo v repozitáři, do něhož bude aplikace testy ukládat a bude 
je moci i číst a rovnou spouštět, a navíc veškerá historie generovaných testů, uložených projektů a uživatelských příběhů, bude uložena v souboru, který bude možno distribuovat přes Git.

\subsection{Architektura systémových komponent}

Nejprve v úvahu přicházela možnost navrhnout systém jako čistě backendovou službu, která by běžela jen v terminálu a komunikovala s uživatelem pouze prostřednictvím CLI,
ale tento přístup by nebyl uživatelsky přívětivý pro ne-technické uživatele. Na základě toho bude systém navržen jako 
\textit{full-stack} aplikace, která bude mít intuitivní GUI a umožní tak širší adopci napříč různými uživateli a týmy.

Schéma architektury bude rozděleno do 4 hlavních logických částí a jejich vzájemná komunikace je znázorněna na obrázku \ref{fig:architecture}.

\begin{figure}[h]
    \centering
    \includegraphics[width=1\textwidth]{pictures/arch.png}

\end{figure}
\subsubsection*{Frontend (Uživatelské rozhraní)}
Tato klientská část zajišťuje interakci s uživatelem a slouží jako hlavní bod pro konfiguraci a vizualizaci celého procesu generování testů.
S backendem bude komunikovat pomocí dvou odlišných komunikačních vzorů. Pro standardní operace čtení a zápisu dat 
(např. zakládání projektů, správa uživatelských příběhů) bude využíváno klasické \texttt{HTTP/REST} rozhraní.
Pro sledování myšlenek agenta při generování ale synchronní HTTP komunikace není ideální, protože potřebujeme průběžně 
aktualizovat uživatelské rozhraní o nové informace (co agent dělá, jaké nástroje volá). Proto bude využit jednosměrný protokol 
\texttt{Server-Sent Events (SSE)}, který umožňuje efektivní streamování dat z backendu na frontend v reálném čase a je alternativou 
k WebSocketům, které jsou pro tento účel komplexnější.


\subsubsection*{Backend}
Nejdůležitější část celé architektury - její hlavní zodpovědností je řízení celého procesu generování testů, udržování agentní smyčky a 
zprostředkování komunikace mezi jazykovými modely, testovacím frameworkem a uživatelským rozhraním. 
Bude zodpovědný také za bezpečné čtení a zápis dat do lokálního konfiguračního souboru.

\subsubsection*{AI Gateway}
Zajištění spolehlivé komunikace s velkými jazykovými modely představuje zásadní výzvu. Každý poskytovatel (provider) 
umělé inteligence (OpenAI, Anthropic, Google) využívá pro své API zcela odlišná vstupní a výstupní schémata - 
liší se formáty pro definici dostupných nástrojů (\texttt{tool calling}), což je pro správnou funkčnost agenta klíčové.
Dále se liší i strukturováním historie zpráv či výpočtem spotřebovaných tokenů - další klíčový faktor pro správné fungování agenta.
Přímá integrace těchto jednotlivých API by vedla k vysoké komplexitě zdrojového kódu a obtížné udržitelnosti.
Pro každého nového poskytovatele by bylo potřeba naimplementovat vlastní logiku pro překlad požadavků a zpracování odpovědí.
Systém proto zavede dedikovanou vrstvu AI Gateway, která tyto rozdíly efektivně abstrahuje za pomoci existujících řešení
(např. knihovny \texttt{AI Vercel SDK}) a díky níž bude budoucí rozšiřitelnost o nové modely výrazně jednodušší - 
bude pouze třeba přidat existující adaptér pro daného poskytovatele, aniž by bylo potřeba zasahovat do zbytku architektury či 
psát ručně překlad pro každý model.


\subsubsection*{MCP Server a testovací framework}
Pro zajištění modularity a bezpečnosti systému by autonomní agent neměl mít přímou kontrolu nad prohlížečem z backendu.
Místo toho budou požadavky na interakci s prohlížečem odesílány do dedikovaného serveru, který bude využívat
standardizovaný \texttt{Model Context Protocol} a poběží jako zcela samostatný izolovaný proces. 
Tento server bude přijímat příkazy od agenta (např. kliknutí na tlačítko, vyplnění formuláře) a překládat 
je do konkrétních instrukcí pro zvolený testovací framework. Framework poté ovládá webový prohlížeč a vrací zpět výsledky akce,
které backend předá agentovi pro další zpracování.


\subsection{Architektura agenta a exekuční smyčka}
\subsubsection*{Zdůvodnění Single-agent architektury}
Jak popisuje příručka OpenAI \cite{openai2025_agents_guide}, existují dva hlavní přístupy k návrhu agentních systémů - \textbf{Single-agent} a \textbf{Multi-agent} architektura,
které jsou zobrazeny na obrázku \ref{fig:agent_architecture}.

\begin{figure}[H]
    \centering
    \includegraphics[width=1\textwidth]{pictures/agent_architecture.pdf}
    \caption{Schéma Single-agent vs Multi-agent architektury.}
    \label{fig:agent_architecture}
\end{figure}


Single-agent architektura se zaměřuje na jednoho centrálního agenta, který má přístup ke všem nástrojům a informacím potřebným k vykonání úkolu.
Tento agent je zodpovědný za celý proces - od plánování, přes exekuci, až po generování výstupu. Tento přístup je jednodušší na implementaci,
snadněji se ladí a chová se determiničtěji, protože veškeré rozhodování je centralizované v jednom agentovi.

Oproti tomu multi-agentní architektura rozděluje úkol mezi více specializovaných agentů, kde každý z nich má svou specifickou roli - 
jeden může být zodpovědný za plánování, druhý za generování kódu a třetí za revizi kódu. Tento přístup může být efektivní pro řešení komplexnějších úloh,
ale přináší s sebou vyšší míru nedeterminismu (jelikož agenti mohou mít různé strategie), je náchylný k zacyklení (nekonečné debaty mezi jednotlivými agenty) a 
jeho debugging je složitý, jelikož je třeba sledovat flow mezi více entitami. Navíc tento způsob může generovat obrovskou režii v podobě spotřebovaných tokenů právě díky 
komunikaci mezi agenty, která vyžaduje další volání modelů.

Proto systém bude využívat striktní Single-agent architekturu, kde bude definován agent s rolí \textit{Senior QA Automation Engineer}, který bude provádět celý proces postupně - 
od prvotní navigace, přes ověření stávajícího stavu aplikace až po finální generování kódu.

\subsubsection*{ReAct smyčka}
Jak bylo popsáno v kapitole dedikované analýze LLM agentů,
systém bude využívat paradigma ReAct. V rámci fáze Thought bude agent analyzovat aktuální stav aplikace a plánovat další krok, který by měl podniknout.
V Action fázi bude volat konkrétní nástroje prostřednictvím MCP serveru, aby získal potřebné informace o stavu aplikace.
V Observation fázi bude backend zpracovávat výsledky těchto akcí a poskytovat jejich zpětnou vazbu agentovi, který na základě toho 
bude pokračovat v iteraci, dokud nebude mít dostatek informací na vygenerování finálního testu.

\subsubsection*{Ochranné mechanismy}
K snížení rizika halucinací bude agent instruován sadou striktních pravidel, 
která bude muset dodržovat. Bude se jednat o následující mechanismy:

\begin{itemize}
    \item \textbf{Tool Enforcement} - Agent bude muset použít nástroje pro průzkum aplikace předtím, než bude moci vygenerovat finální test. Běžně se stává, že agenti se snaží rovnou
    vygenerovat test ``naslepo``, aniž by měli dostatek informací o stavu aplikace.
    \item \textbf{Code Validation} - Jakmile agent vygeneruje kód, bude muset projít základní validací, aby se ověřilo, že je syntakticky správný a přeložitelný. Pokud ne,
    bude agent vyzván k opravě kódu, dokud nebude kód validní.
    \item \textbf{Circuit Breaker} - Aby se předešlo nekonečnému zacyklení (které by vyústilo v nekonečné volání LLM modelů), 
    bude implementován mechanismus, který po určitém počtu po sobě jdoucích selhání nástrojů přeruší agentní smyčku a ukončí proces generování testu.
\end{itemize}

Tento přístup by měl zlepšovat spolehlivost a kvalitu vygenerovaných testů a zároveň minimalizovat náklady spojené s opakovanými voláními modelů.

\subsection*{Vizualizace procesu agenta}
Tato sekce bude klíčová pro zajištění transparentnosti a důvěry uživatelů v systém. 
Bude zobrazovat celý průběh generování testů - od prvotního zamyšlení agenta, přes volání nástrojů až po finální validaci a generaci kódu. Pokud to 
daný krok umožní, bude zobrazovat i konkrétní výstup (např. výsledek tool callu). Po vygenerování testu bude (kromě samotného kódu) zobrazeno 
i krátké shrnutí v podobě počtu zkonzumovaných tokenů, celkové ceny a případně i možnost regenerovat test na základě zpětné vazby od uživatele.

\subsection*{Sekce pro spuštění testů a zobrazení výsledků}
Tato sekce by měla nahradit potřebu přepínat mezi běžícím systémem pro generování testů a vývojovým prostředím, čímž se vývojářům ušetří čas.
Uživatel by měl mít možnost vidět a spravovat testy, které má v aktuálním repozitáři - a pokud možno, tak je rovnou i spouštět a vidět výsledky jejich běhu.

\section{TypeScript}
Jako primární programovací jazyk celého systému byl zvolen TypeScript.
Jedná se o striktně typovanou nadstavbu jazyka JavaScript, která do webového vývoje přináší statickou kontrolu typů \cite{bierman2014understanding, richards2015concrete}.
Hlavní výhodou této technologie je schopnost detekovat typové a strukturální chyby již během fáze vývoje a kompilace, na rozdíl 
od JavaScriptu, který tyto chyby odhalí až při samotném běhu aplikace. Tato schopnost je pro navrhovaný systém klíčová, 
protože vzhledem k neustálé a dynamické výměně dat mezi frontendem, backendem a velkými jazykovými modely je 
zajištění konzistentních datových struktur naprosto nezbytné pro správnou funkčnost, spolehlivost a udržitelnost.

To bude realizováno prostřednictvím DTO (Data Transfer Object) patternu, kdy budou definovány konkrétní 
datové typy a rozhraní pro všechny klíčové entity systému (projekty, uživatelské příběhy, vygenerované testy).
Díky tomu bude možné sdílená rozhraní definovat pouze jednou napříč celou aplikací, 
což výrazně zjednodušuje vývoj, eliminuje redundantní kód a snižuje riziko chyb.

\section{React}
Pro vývoj uživatelského rozhraní byla zvolena populární javascriptová knihovna React. 
Disponuje deklarativním a komponentovým přístupem, díky němuž je možné rozdělit komplexní rozhraní do menších, znovupoužitelných částí.
Vzhledem k důrazu na maximální interaktivitu navrhovaného systému (zejména pro dynamické vykreslování myšlenkových pochodů agenta, 
správu stavu rozhraní pro specifikaci uživatelských příběhů či zobrazení výsledků vygenerovaných testů) je efektivní správa stavu 
komponent klíčová. Zásadním benefitem Reactu je využití tzv. virtuálního DOMu (Virtual DOM), který zaručuje, 
že se při změně stavu překreslí pouze ta část uživatelského rozhraní, jež se skutečně změnila \cite{chen2019front}. To výrazně 
zlepšuje výkon a zajišťuje plynulý chod aplikace i při velkém počtu příchozích událostí.
Dalším rozhodujícím faktorem pro volbu této knihovny byla podpora jazyka TypeScript prostřednictvím syntaxe TSX,
což umožňuje bezproblémově napojit frontend na sdílené DTO modely a zachovat striktní typovou bezpečnost napříč celou aplikací.

\section{NestJS}
Pro vývoj backendové části aplikace byl zvolen framework NestJS založený na platformě Node.js.
Tento framework byl vybrán především pro svou modulární architekturu a integrovanou podporu pro \textit{Dependency Injection} -
klíčový návrhový vzor pro udržitelnost a testovatelnost kódu \cite{munirov2025nestjs}. Vzhledem k tomu, že agent bude obsahovat komplexní logiku,
která zahrnuje komunikaci s LLM, správu lokálního souborového systému, správu uživatelských příběhů a projektů, 
je důležité, aby tyto domény byly striktně logicky oddělené do samostatných modulů, což povede k lepší čitelnosti, testovatelnosti 
a dlouhodobé udržitelnosti celého backendu. NestJS navíc nabízí nástroj \texttt{Nest CLI}, který umožňuje 
rychlé generování boilerplate kódu pro nové moduly, služby a kontrolery, což výrazně usnadňuje a zrychluje vývoj.
Na rozdíl od klasického Express.js podporuje nativně i asynchronní streamování dat pomocí SSE, díky čemuž je eliminována 
potřeba implementovat komplexnější řešení na bázi WebSocketů. 


Jak je vidět na obrázku \ref{fig:sseVsSocket}, pro tento případ použití je SSE vhodnou volbou. 
Zatímco WebSockety vyžadují udržování obousměrného spojení, SSE funguje na principu standardního HTTP požadavku, 
kdy klient pouze otevře spojení (\texttt{GET /sse}) a následně server už jen jednosměrně odesílá průběžné aktualizace směrem k uživateli.

\section{Vercel AI SDK}
Pro komunikaci s velkými jazykovými modely (LLM) byla zvolena knihovna Vercel AI SDK. 
Jak již bylo zmíněno v předchozí kapitole, největším úskalím integrace různých poskytovatelů umělé 
inteligence je značná rozdílnost specifikací jejich API. Vercel AI SDK tento problém elegantně řeší tím,
 že funguje jako univerzální adaptér. Poskytuje jednotné rozhraní, díky kterému lze, jak uvádí 
 Patil et al. ve studii \textit{Real time inventory management system powered by generative user interface} \cite{patil2024real}, plynule přecházet mezi různými modely pouhou úpravou konfigurace, 
 aniž by bylo nutné zasahovat do vnitřní logiky agenta.

Zásadním důvodem ale byla podpora pro volání nástrojů - knihovna nativně řeší překlad definic nástrojů (pomocí JSON schémat)
do formátů specifických pro jednotlivé poskytovatele a automaticky parsuje a validuje odpovědi od modelů zpět do striktně typovaných TypeScript objektů.

V neposlední řadě nabízí i spoustu předpřipravených hooků pro React/Next.js aplikace a podporuje streamování odpovědí.


\section{Playwright a Model Context Protocol (MCP)}
Jako finální testovací framework byl zvolen Playwright. 
Jak popisuje studie \textit{Automated end to end testing with Playwright for React applications} \cite{talakola2024automated}, Playwright efektivně řeší specifické výzvy moderních dynamických aplikací, 
jako jsou asynchronní operace, složité překreslování komponent a komplexní správa stavu. 
Přestože byly základní výhody tohoto nástroje představeny v teoretické části, 
níže jsou na základě zmíněné studie shrnuty ty nejzásadnější, které rozhodly o jeho výběru pro tento systém:

\begin{itemize}
    \item \textbf{Pokročilý Auto-waiting a stabilita:} Framework automaticky vyčkává na interaktivitu prvků, čímž eliminuje potřebu statických čekacích dob a radikálně snižuje nestabilitu testů.
    \item \textbf{Network Interception a API Mocking:} Nativní podpora zachytávání síťového provozu umožňuje simulovat chybové stavy a podvrhovat API odpovědi bez nutnosti úprav na skutečném backendu.
    \item \textbf{Složité uživatelské interakce:} Nástroj spolehlivě zvládá práci se Shadow DOM, testování napříč více záložkami a komplexní akce typu \textit{drag-and-drop}.
\end{itemize}

Pro integraci s autonomním agentem je navíc klíčová dostupnost NPM balíčku \texttt{@playwright/mcp}, 
který běží jako samostatný proces a komunikuje s backendem přímo přes protokol MCP.

\section{Organizace projektu}

Celý systém byl implementován jako tzv. monorepo (monolithic repository) s využitím nástroje Turborepo,
který umožňuje spravovat více logicky oddělených aplikací, knihoven či služeb v rámci jednoho repozitáře.
Díky tomu je možné sdílet kód, typy a rozhraní napříč různými častmi systému bez nutnosti publikovat a spravovat
samostatné balíčky pro každou z těchto částí. Nástroj Turborepo navíc optimalizuje proces sestavování (build process)
díky inteligentnímu cachování, které zajišťuje, že se znovu sestaví pouze ty části systému, které byly skutečně změněny, 
což výrazně zrychluje vývoj a testování.

Základní struktura projektu je rozdělena do dvou hlavních adresářů - složka \texttt{apps} pro spustitelné aplikace (backend a frontend) a 
složka \texttt{packages} pro sdílené knihovny (např. pro DTO modely, CLI nástroje).
Zjednodušené zobrazení této struktury je znázorněno níže:

kompilaci, čímž se výrazně snižuje riziko neúmyslných chyb a naplňuje tak požadavek na striktní typovou bezpečnost napříč celou aplikací.

Cílem je představit logickou architekturu serveru, klíčové moduly a jejich zodpovědnosti - konkrétní 
detaily implementace budou představeny v rámci dalších sekcí. 


\subsection{Doménové moduly}

Backendová část (\texttt{apps/api}) je postavena na frameworku NestJS a dodržuje jeho modulární architekturu.
Aplikace je rozdělena do nezávislých doménových modulů, které jsou pak jako jednotlivé funkční celky sdružené v hlavním vstupním bodě 
(\texttt{AppModule}). Architektura je logicky vrstvena do tří hlavních domén, které jsou zobrazeny na
obrázku \ref{fig:backend_modules}.

\begin{figure}[H]
    \centering
    \includegraphics[width=1\textwidth]{pictures/app_architecture.pdf}
    \caption{Zjednodušený diagram vrstvených závislostí backendových modulů.}
    \label{fig:backend_modules}

Díky této separaci je zajištěno, že každý modul má jasně definovanou zodpovědnost, což výrazně zlepšuje nejen čitelnost a udržitelnost kódu,
ale i jeho testovatelnost. Každý modul může být jednoduše testován izolovaně pomocí unit testů a následně i integračních testů,
které ověří správnou spolupráci mezi moduly.


Tok dat (Request/Response flow) uvnitř backendu je striktně vrstvený a dodržuje best practices zapouzdření. 
Požadavek z klientské aplikace je nejdříve zachycen v příslušném kontroleru dané domény (např. \texttt{AgentController}),
který provádí počáteční validaci vstupních parametrů pomocí DTO a Zod schémat. Kontroler nikdy nekomunikuje s konkrétními 
službami z jiných modulů - od toho je tu dedikovaná servisní vrstva (např. \texttt{AgentOrchestrationService}), 
která zapouzdřuje veškerou business logiku.
Až tato vrstva deleguje dílčí úkoly dál a bezpečně komunikuje se specializovanými službami (Services) z jiných modulů. 

\subsubsection*{Core AI Orchestration}
Tato vrstva tvoří jádro celého systému a obsahuje moduly zodpovědné za interakci s velkými jazykovými modely a jejich orchestraci.
\texttt{AgentModule} implementuje řídící smyčku agenta a orchestrace běží přes služby \texttt{AgentService} a \texttt{AgentOrchestrationService}.
Zároveň tento modul přímo integruje \texttt{LlmModule}, \texttt{ToolsModule}, \texttt{ProjectsModule}, \texttt{UserStoriesModule}, \texttt{StorageModule} a \texttt{FileStorageModule},
což z něj dělá hlavní integrační bod backendu.
\texttt{LlmModule} poskytuje jednotné rozhraní pro volání různých poskytovatelů modelů přes AI Gateway,
\texttt{ToolsModule} pak dále zajišťuje načtení dostupných nástrojů a jejich exekuci přes MCP vrstvu - aktuálně s podporou Playwright nástrojů, ale
s možností snadného budoucího rozšíření \textbf{(NFR-05)}.

\subsubsection*{Business Domain Modules}
Tyto moduly reprezentují doménovou logiku aplikace. \texttt{ProjectsModule} zajišťuje správu projektů a jejich konfigurací,
\texttt{UserStoriesModule} spravuje uživatelské příběhy a jejich artefakty (název, popis, akceptační kritéria), 
a \texttt{TestsModule} zajišťuje načítání, spouštění a mazání již vygenerovaných Playwright testů.
Samotné generování testů je řízeno přes endpointy modulu \texttt{AgentModule}; \texttt{TestsModule} slouží primárně pro exekuci a správu výsledných testovacích souborů.

\subsubsection*{Infrastructure \& Persistence}
Nejnižší vrstva zajišťuje veškeré nefunkční aspekty - od konfigurace přes management dat v cache až po bezpečný zápis do souborového systému.
\texttt{ConfigModule} zajišťuje načtení proměnných prostředí a práci s lokálním konfiguračním souborem,
\texttt{StorageModule} ukládá metadata o generování do souboru.
\texttt{FileStorageModule} se stará o zápis vygenerovaných testů do cílového adresáře, vytváření složek a řešení kolizí názvů souborů.


\subsection{Implementace doménového modelu a sdílených DTO}
Navrhovaný doménový model z kapitoly 3 byl v rámci implementace převeden do sdílených TypeScript interfaců, které jsou umístěny v balíčku \texttt{packages/shared} 
a přímo využívány jak frontendem, tak backendem. Struktura balíčku \texttt{shared} je rozdělena do dvou hlavních složek:
\begin{itemize}
    \item \texttt{/types} - Obsahuje doménové entity jako \texttt{Project}, \texttt{UserStory} a \texttt{TestPilotConfig}. 
    Jedná se o konkrétní doménové objekty, které reprezentují perzistovaná data v systému.
    \item \texttt{/dto} - Obsahuje Data Transfer Objects pro jednotlivé operace (Create, Update, Response). 
    Zajišťují konzistentní datové struktury pro API vrstvu a komunikaci mezi klientem a serverem.
\end{itemize}

Definice dvou klíčových doménových entit - \texttt{Project} a \texttt{UserStory} -

rozšířeny o metainformace jako \texttt{createdAt} a \texttt{updatedAt},

auditování nebo zobrazení časové osy projektu.

kolik tokenů bylo zkonzumováno, jaká byla celková cena a (v případě úspěchu) i samotný vygenerovaný kód testu. 
Tyto informace jsou klíčové pro zpětnou vazbu uživatelům a budou dále zmíněny a využity v další kapitole,
která se zaměří na testování funkčnosti systému a celkové náklady generování testů.


Klíčovým problémem při práci s těmito soubory je synchronizace kritických sekcí typu \textit{read-modify-write}.
Při paralelních požadavcích by mohlo dojít k nechtěnému přepsání, ztrátě či poškození dat (např. v případě kolizí při souběžném zápisu do souborů).
Proto byl pro eliminaci tohoto rizika implementován asynchronní zámek (promise-based mutex), který zajistí, 
že všechny operace, které modifikují obsah těchto souborů, budou striktně serializované. Před každým zápisem je navíc 
načtený obsah souborů validován proti definovaným Zod schématům, což zajišťuje další úroveň ochrany proti nekonzistentním datům.

\section{Implementace komunikace s LLM}
Modul \texttt{LlmModule} představuje komunikační rozhraní mezi vnitřní logikou systému 
(autonomním agentem) a providery velkých jazykových modelů.
Hlavním úkolem této vrstvy bylo zajistit takovou abstrakci, 
která by umožnila snadnou integraci nových poskytovatelů a modelů, čímž 
se minimalizovalo riziko závislosti na konkrétním provideru (\textit{vendor lock-in}) \textbf{(NFR-04)}.
Díky tomu je přidání podpory pro nové modely pouze záležitostí několika
řádků kódu (v případě nového providera vytvoření nového souboru s jeho modely).

\subsection{Abstrakce poskytovatelů a Vercel AI SDK}
Jak již bylo zmíněno, problém abstrakce různých poskytovatelů řeší knihovna Vercel AI SDK.
Systém na úrovni \texttt{LlmService} pracuje s jednotným formátem zpráv a nástrojů.
Na ukázce \ref{lst:llm-generic} je zobrazen způsob volání modelu přes funkci \texttt{generateText}.
Je vidět, že se předávají pouze obecné parametry jako je identifikátor modelu, systémový prompt, 
předchozí zprávy a dostupné nástroje - žádné konkrétně nadefinované struktury pro jednotlivé providery.

\begin{lstlisting}[style=tscode, caption={Ukázkové volání LLM přes Vercel AI SDK.}, label={lst:llm-generic}]
import { generateText } from 'ai';

const result = await generateText({
    model: "anthropic/claude-sonnet-4.6",
    system,
    messages,
    tools,
    temperature,
});

return {
    text: result.text,
    toolCalls: result.toolCalls,
    usage: result.usage,
};
\end{lstlisting}

Pak již stačí jen do systémových proměnných nastavit odpovídající klíče jednotlivých providerů 
a je možné bez jakýchkoliv dalších úprav přepínat mezi modely pouhou změnou identifikátoru modelu v proměnné \texttt{model}.
Nevýhodou tohoto přístupu v komerční praxi je, že pokud by chtěl uživatel volat všechny firemní modely, 
musel by mít přístup ke všem potřebným klíčům a nastavit je v prostředí, což není ideální z pohledu bezpečnosti a správy přístupů.
S tím souvisí i pricing - pokud by uživatel začal neúmyslně volat dražší modely, mohl by se mu rychle navýšit účet za využití API.

Tento problém v implementovaném řešení eliminuje vlastní integrační vrstva. 
Ta za pomoci funkce \texttt{createOpenAICompatible}, která je součástí Vercel AI SDK, 
umožňuje definovat vlastní mapování modelů a jejich identifikátorů. V praxi to znamená, 
že systém v rámci konfigurace využívá jeden univerzální API klíč pro podnikovou AI Gateway a 
pomocí něj má přístup ke všem podporovaným modelům. Tím se zásadně zvyšuje bezpečnost - klíče 
různých poskytovatelů nejsou distribuované napříč klientskými zařízeními, ale jsou bezpečně spravovány 
na straně gateway \textbf{(NFR-03)}. Koncový uživatel (nebo konkrétní instance aplikace) pak využívá pouze jeden vygenerovaný klíč, 
což umožňuje detailní monitoring a případné omezení využití jednotlivých modelů (rate limiting). To je naprosto klíčové 
pro kontrolu nákladů.

V rámci této práce byl proto využit právě tento přístup, kdy uživatel dostane jeden univerzální API klíč pro AI Gateway firmy 
Emplifi, přes níž se následně volají všechny podporované modely. To výrazně zjednodušuje použití tohoto systému 
zaměstnanci a zároveň umožní na konci vývoje a testování určit, kolik nákladů bylo na tento systém vynaloženo, což
bude důležitá metrika pro zhodnocení efektivity navrženého řešení.

\begin{lstlisting}[style=tscode, caption={Zjednodušené napojení Vercel AI SDK na vlastní AI Gateway}, label={lst:llm-custom-provider}]
private gateway = createOpenAICompatible({
    name: 'ai-gateway',
    apiKey: this.configService.aiGatewayKey,
    baseURL: this.configService.aiGatewayBaseUrl,
});

async generate(request: Request, signal?: AbortSignal): Promise<Response> {
    const model = this.models.get(request.model)!;
    const modelId = this.resolveGatewayModelId(model); 
    const messages = this.convertMessagesToAISdk(request.messages);
    const tools = this.convertToolsToAISdk(request.tools);
    const temperature = request.temperature ?? 0;

    const result = await generateText({
        model: this.gateway(modelId),
        system: request.system,
        messages,
        tools,
        ...(model.supportsTemperature !== false && { temperature }),
        abortSignal: signal,
    });

    return this.convertResponse(result, model);
}
\end{lstlisting}

Na ukázce \ref{lst:llm-custom-provider} je zobrazen způsob, jakým je Vercel AI SDK napojeno na vlastní AI Gateway.
Nejprve se pomocí funkce \texttt{createOpenAICompatible} vytvoří instance gateway, 
která je nakonfigurovaná s univerzálním API klíčem a základní URL pro volání modelů.
Následně se v metodě \texttt{generate} připraví všechny potřebné parametry pro volání modelu - 
identifikátor modelu se přeloží na odpovídající ID pro AI Gateway (jelikož např. Anthropic modely jsou 
poskytovány přes AWS Bedrock, a proto mají jiné ID než stejné modely volané přímo přes Anthropic API),
zprávy a tooly se převedou do očekávaného formátu pro Vercel AI SDK a nakonec se zavolá 
funkce \texttt{generateText} s připravenými parametry. Výsledek se pak převede do interního formátu.
Jak je vidět, funkce \textsl{generateText} umožňuje nastavovat i další parametry jako je \texttt{temperature} pro modely, 
které tento parametr podporují, či \texttt{abortSignal} pro možnost přerušení běhu generování, což je klíčové pro zajištění 
dobré uživatelské přívětivosti a kontroly nad procesem generování testů.

by výrazně omezily rozsah testování. Cílem práce je ověřit navržené řešení v reálných podmínkách, 
což zahrnuje i důraz na ekonomickou efektivitu, nikoliv pouze dosažení nejlepší možné kvality bez ohledu na náklady.

\subsubsection*{Výpočet ceny generování}
Po každém volání modelu se z \texttt{result.usage} načtou počty tokenů
\texttt{inputTokens}, \texttt{outputTokens} a \texttt{cachedInputTokens}.
Poté se cena vypočte přímo v metodě \texttt{calculateCost} (jak je uvedeno v ukázce \ref{lst:llm-cost-calc}) a následně 
přičte k záznamu o generování, který se po skončení běhu uloží do cache souboru \texttt{.testpilot-cache.json}.


\begin{lstlisting}[style=tscode, basicstyle=\ttfamily\scriptsize, caption={\protect\centering Výpočet ceny LLM dotazu.}, label={lst:llm-cost-calc}]
private calculateCost(
    inputTokens: number, 
    outputTokens: number, 
    cachedTokens: number, 
    pricing: LLMModelDefinition['pricing']
) {
    const nonCachedInputTokens = Math.max(0, inputTokens - cachedTokens);
    const cachedRate = pricing.cached ?? 0;

    return {
        input: (nonCachedInputTokens / 1e6) * pricing.input,
        output: (outputTokens / 1e6) * pricing.output,
        cached: (cachedTokens / 1e6) * cachedRate,
    };

}
\end{lstlisting}

\section{Implementace autonomního agenta}
\subsection{Integrace nástrojů přes Model Context Protocol}

Pro integraci nástrojů backend nevolá Playwright API přímo, ale využívá dedikovanou vrstvu \texttt{PlaywrightMCPTools},
jež inicializuje MCP klienta (\texttt{MCPClient}). Jak je vidět na ukázce \ref{lst:mcp-integration-code}, 
klient je nakonfigurován pomocí příkazu \texttt{npx} a balíčku \texttt{@playwright/mcp}.
Serverová část MCP tak běží jako samostatný proces komunikující přes I/O, což zajišťuje procesní izolaci a 
zotavitelnost - selhání prohlížečového runtime nebo pád MCP serveru se neprojeví jako pád hlavního NestJS procesu,
ale jako chyba volání konkrétního nástroje \textbf{(NFR-01)}. 


\begin{lstlisting}[style=tscode, caption={\protect\centering Zkrácený proces inicializace MCP.}, label={lst:mcp-integration-code}]
const config = getToolsConfig();

// Playwright wrapper: create MCP client with values from config
this.mcpClient = new MCPClient(
    'npx',
    ['-y', config.playwright.mcpPackage], // '@playwright/mcp@0.0.68'
    { connectTimeoutMs: config.playwright.connectTimeoutMs }, // 30000
);

// MCP client constructor: stdio transport over child process
this.transport = new StdioClientTransport({
    command: serverCommand,
    args: serverArgs,
});

// MCP client connect(): explicit timeout guard
await this.withTimeout(
    this.client.connect(this.transport),
    this.connectTimeoutMs,
    `MCP connection timed out after ${this.connectTimeoutMs}ms`,
);

// If connection is successful, set connected flag
this.connected = true;
\end{lstlisting}

Pro komunikaci mezi těmito dvěma procesy se využívá \texttt{StdioClientTransport}.
Ten umožňuje přenášet zprávy prostřednictvím standardního vstupu a výstupu (stdio),
což představuje efektivní a jednoduchý způsob pro lokálně spouštěné MCP servery.

Poslední část ukázky demonstruje způsob, jakým se aplikace chrání před potenciálním uvíznutím.
Jelikož se spouští zcela nový a nezávislý proces, existuje riziko, že spojení selže nebo server přestane 
při inicializaci reagovat (např. kvůli problémům s prostředím, nedostatečným oprávněním, nebo jiným neočekávaným chybám).
Z tohoto důvodu je proces navázání spojení (\texttt{client.connect}) obalen asynchronním timeoutem (\texttt{withTimeout}), 
který zajistí, že pokud se spojení nepovede navázat do určitého časového limitu,
 bude operace ukončena chybou a systém zůstane v konzistentním stavu (\texttt{connected = false}).


\subsection{Řídící smyčka agenta a ochranné mechanismy}

Veškerá agentova logika je implementována v rámci \texttt{AgentService}, 
která je zodpovědná za řízení hlavní smyčky exekuce, správu vnitřního stavu a implementaci ochranných mechanismů.
Tyto funkce jsou detailně popsány níže.


\subsubsection*{Správa vnitřního stavu exekuce (State Management)}
Jak bylo zmíněno v předchozích kapitolách, agent pracuje v rámci iterativních smyček, 
a proto je nutné udržovat celý kontext napříč jednotlivými iteracemi.
Pro tento účel byl navržen \texttt{AgentExecutionState}, který je zobrazen na ukázce \ref{lst:agent-state}. 

\begin{lstlisting}[
  style=tscode,
  basicstyle=\ttfamily\scriptsize,
  float=false,
  caption={\protect\centering Struktura vnitřního stavu exekuce agenta.},
  label={lst:agent-state},
  morekeywords={ToolCallResult,Message,TokenUsage,Cost,AgentIterationLog}
]
interface AgentExecutionState {
  iteration: number;
  conversationMessages: Message[];
  allToolCalls: ToolCallResult[];
  successfulToolCalls: ToolCallResult[];
  failedToolCalls: ToolCallResult[];
  consecutiveToolFailures: number;
  iterationLogs: AgentIterationLog[];
  totalTokenUsage: TokenUsage;
  totalCost: Cost;
}
\end{lstlisting}

Jak je vidět, stav obsahuje všechny klíčové informace potřebné pro řízení exekuce.
Počínaje číslem aktuální iterace (\texttt{iteration}), přes celou historii konverzace s LLM (\texttt{conversationMessages}), 
až po detailní záznamy o všech voláních nástrojů (\texttt{allToolCalls}, \texttt{successfulToolCalls}, \texttt{failedToolCalls}, \texttt{consecutiveToolFailures}).
Pro případnou zpětnou analýzu či ladění jsou uchovávány i kompletní záznamy o průběhu jednotlivých iterací (\texttt{iterationLogs}), 
které obsahují informace o vstupních zprávách, nástrojích, odpovědích modelu, využití tokenů a dalších relevantních datech.
V neposlední řadě jsou v rámci stavu udržovány i nasčítané statistiky o celkovém množství využitých tokenů (\texttt{totalTokenUsage}) 
a celkových nákladech (\texttt{totalCost}).

\subsubsection*{Ochranné mechanismy a řízení běhu}

Přestože je chování modelu primárně řízeno systémovým promptem (viz další subsekce), 
systém nemůže spoléhat pouze na to, že model bude vždy správně interpretovat a dodržovat instrukce (halucinování).
Proto \texttt{AgentService} implementuje ochranné mechanismy představené v kapitole \ref{chapter:system_design}, které 
agenta omezují zvenčí.

Tyto mechanismy jsou zobrazeny v ukázce \ref{lst:agent-loop}, která představuje zjednodušený pseudokód hlavní řídící smyčky agenta.

\begin{lstlisting}[
  style=tscode,
  basicstyle=\ttfamily\scriptsize,
  caption={\protect\centering Zjednodušená řídicí smyčka agenta.},
  label={lst:agent-loop}
]
while (state.iteration < config.maxIterations) {
  // Cancellation Check  
  if (signal?.aborted)
    return this.handleCancellation(...);

  // Circuit Breaker  
  if (state.consecutiveToolFailures >= config.maxConsecutiveToolFailures)
    await this.generationRecord.createFailure(...);

  state.iteration++;
  const response = await llmService.generate(...);
  const toolUses = extractToolUses(response);

  if (toolUses.length === 0) {
    const result = await handleNoToolCalls(...);

    if (result.type === 'continue') continue;
    if (result.type === 'error') throw new Error(result.error);
    if (result.type === 'success') return result.response;
  }

  await this.processToolCalls(...);
}

this.handleMaxIterationsReached(...);

\end{lstlisting}



Smyčka je omezena na maximální počet iterací (\texttt{config.maxIterations}), 
aby se zabránilo nekonečnému běhu v případě halucinací, nečekaných chyb či jiných problémů.
Pro případ, že by uživatel chtěl generování kdykoliv přerušit, obsahuje smyčka i kontrolu pro zrušení pomocí \texttt{AbortSignal}.
Další důležitou ochranou je \textbf{Circuit Breaker}, který sleduje počet po sobě jdoucích selhání nástrojů.
Pokud tento počet překročí nastavený limit (\texttt{config.maxConsecutiveFailures}), smyčka se okamžitě přeruší a vrátí chybu, 
aby se opět zabránilo dalšímu volání LLM a s tím i spojeným nákladům \textbf{(NFR-02)}. Následně se navýší číslo iterace, připraví se požadavek 
pro LLM a vykoná pomocí metody \texttt{llmService.generate}. 
Po obdržení odpovědi se z ní extrahují požadavky na nástroje. 

Pokud LLM nepožaduje použití žádných nástrojů, spustí se metoda \texttt{handleNoToolCalls}, 
která analyzuje odpověď a rozhodne, zda je potřeba pokračovat v dalších iteracích - 
např. zmiňovaný \textbf{Tool Enforcement}, který vynutí použití dalších nástrojů - nebo zda 
je odpověď potřeba opravit (Code Validation - bude vysvětlen v nadcházející subsekci). 
Pokud se jedná již o finální zvalidovaný kód (\texttt{result.type === 'success'}), 
smyčka se ukončí a vygenerované testy se vrátí uživateli.
Pokud ale model nějaké volání nástrojů požaduje,
spustí se metoda \texttt{processToolCalls}, která se postará o jejich vykonání, zpracování výsledků a aktualizaci stavu agenta.

Tento přístup se opakuje do doby, než agent dosáhne úspěšného ukončení (získá validní testy bez potřeby volání dalších nástrojů) 
nebo překročí nastavený limit iterací, případně dojde k přerušení uživatelem či aktivaci circuit breakeru. Pokud dojde ke zmiňovaným 
přerušením, logika opustí smyčku a (v případě aktivace circuit breakeru) se metoda \texttt{handleMaxIterationsReached} postará o vytvoření 
záznamu o neúspěšném pokusu o generování testů a informování uživatele o důvodu neúspěchu.

\subsection{Návrh systémového promptu a řízení chování (Prompt Engineering)}
Tato část se zaměřuje na nejdůležitější aspekt celého systému - návrh systémového promptu, 
který je základem pro řízení chování LLM a tím i pro úspěšné generování testů.
Z důvodu rozsáhlosti jsou plná znění systémového i regeneračního promptu k dispozici v příloze \ref{app:prompts}. 
Prompty jsou zapsány v Markdown formátu, který umožňuje lepší strukturování a čitelnost instrukcí pro model.


\subsubsection*{Struktura a fáze systémového promptu}
Systémový prompt je dynamicky sestavován pomocí funkce \texttt{getSystemPrompt} \textbf{(FR-01)}, která do
něj vkládá kontext konkrétního projektu (název, výchozí URL a popis) a uživatelského příběhu (název, popis, akceptační kritéria a případně 
nepovinnou dodatečnou specifikaci). Model je poté instruován k dodržování přísných pravidel a postupů, 
které jsou rozděleny do několika klíčových sekcí, jak je shrnuto v tabulce \ref{tab:prompt-structure}.

Důležité bylo zajistit, aby si agent uměl poradit nejen s ideálními scénaři, ale aby byl schopen i detekovat 
funkcionální mezery - např. když uživatelský příběh požaduje určitou funkcionalitu, která v reálné aplikaci chybí nebo je rozbitá.
Prompt tento problém řeší zavedením konceptu \textbf{řízeného selhání} - pokud agent zjistí, že 
požadovaná funkcionalita chybí nebo je rozbitá, je instruován tak, aby se pokusil napsat test pokrývající správné, očekávané chování.
Tento test se ale následně musí označit pomocí speciálního příznaku \texttt{test.fail()} \textbf{(FR-04)}, 
aby bylo jasné, že se jedná o známou chybu implementace, a navíc se na začátku souboru s vygenerovaným testem 
vytvoří v komentáři blok \texttt{IMPLEMENTATION NOTES}, který popisuje rozdíl mezi zadáním a realitou \textbf{(FR-06)}.


\subsubsection*{Prompt pro regeneraci a iterativní zpětnou vazbu}

Druhým klíčovým aspektem pro řízení chování agenta je schopnost regenerace testu na základě zpětné vazby od uživatele -
a přesně to je realizováno pomocí regeneračního promptu (\texttt{getRegenerationPrompt}) \textbf{(FR-09)}. Hlavní rozdíl mezi 
systémovým a regeneračním promptem je v tom, že regenerační prompt obsahuje navíc i 
\textbf{předchozí vygenerovaný kód} a \textbf{textovou zpětnou vazbu od uživatele}, která popisuje, co je potřeba opravit nebo změnit.
Prompt má poté explicitní instrukci \textit{"Keep what works; change only what is required to address the feedback"}, 
což by mělo vést k minimalizaci rizika, že agent při regeneraci přepíše nebo rozbije již existující funkční 
testy, přičemž má ale stále povinnost ověřovat všechny změny přímo na běžící aplikaci pomocí nástrojů.


\subsection{Validační pipeline a samoopravná smyčka}

Jakmile jazykový model úspěšně dokončí fázi průzkumu a vygeneruje testy, 
je potřeba zajistit, že výstupem je opravdu spustitelný kód \textbf{(FR-05)}.
LLM vrací odpovědi ve formátu Markdown, což znamená, 
že kód je potřeba nejprve extrahovat a až poté validovat, než se vrátí uživateli.
K tomu slouží validační pipeline představená v kapitole \ref{chapter:system_design}, která je implementována v rámci 
\texttt{CodeValidatorService}. Zpracování výstupu je zobrazeno na diagramu \ref{fig:validation-pipeline} 
a skládá se ze tří hlavních fází - extrakce kódu, sémantické kontroly a in-memory TypeScript kompilace, která
může být následována samoopravnou smyčkou v případě zjištění chyb (tzv. \textit{self-correction}).

\subsubsection*{Extrakce kódu a sémantické kontroly}
Prvním krokem je správné extrahování zdrojového kódu z odpovědi modelu.
K detekci kódových bloků se využívají regulární výrazy, které hledají sekce ohraničené třemi zpětnými apostrofy (\texttt{```}) 
s následným označením jazyka (např. \texttt{typescript} nebo \texttt{ts}).
Pokud explicitní označení chybí, využívají se záložní metody pro nalezení generického kódového bloku (nejen s TypeScript tagem, ale i bez něj).
Pokud kódový blok není nalezen vůbec, pipeline se ukončí s chybou a vrátí se zpětná vazba pro LLM, aby kód správně ohraničil.

\subsubsection*{Sémantická kontrola}
Dalším krokem je sémantická kontrola ověřující základní předpoklady pro Playwright testy.
Konkrétně se jedná o:

\begin{itemize}
  \item Kontrola přítomnosti importu z knihovny \texttt{@playwright/test} v případě, že kód obsahuje volání \texttt{test()} nebo \texttt{expect()}.
  \item Ověření, že každý test obsahuje alespoň jednu aserci (\texttt{expect()}), aby nebyl test prázdný.
  \item Detekce použití klíčového slova \texttt{await} mimo \texttt{async} kontext (např. chybějící \texttt{async} u funkce nebo testu).
  \item Kontrola běžných překlepů v API Playwrightu (např. \texttt{getByRoll} místo \texttt{getByRole}, \texttt{waitForSelecter} místo \texttt{waitForSelector} apod.).
\end{itemize}

\subsubsection*{In-memory TypeScript kompilace}
Následuje in-memory kompilace pomocí TypeScript Compiler API, která ověří, 
že kód je nejen syntakticky správný, ale také že neobsahuje hlubší sémantické chyby, které nemohou být odhaleny pouhými regulárními výrazy
(např. nedeklarované proměnné či neplatné typy).
Na rozdíl od klasické diskové kompilace tento přístup eliminuje potřebu vytváření a správu dočasných souborů,
čímž eliminuje problémy s jejich pojmenováním, umístěním či mazáním 
(to by mohlo být obzvláště problematické v prostředí, kde by mohlo docházet k paralelním běhům více agent instancí,
které by mohly navzájem kolidovat s dočasnými soubory). Zároveň poskytuje rychlejší zpětnou vazbu, protože odpadá 
režie spojená s I/O operacemi, což je klíčové pro udržení plynulosti a rychlosti agentovy smyčky.

\subsubsection*{Samoopravná smyčka (Self-correction)}
Pokud kód neprojde sémantickou kontrolou nebo in-memory kompilací, 
systém aktivuje samoopravnou smyčku. Nejprve se zkontroluje, 
zda nebyl překročen limit pro počet pokusů o opravu kódu (\texttt{maxRepairAttempts} s 
výchozí hodnotou 3) a v případě, že byl, pipeline se ukončí s chybou, která se vrátí až orchestrátorovi či uživateli.
V opačném případě se zjištěné chyby (včetně detailů jako je typ chyby, chybová zpráva a číslo řádku) 
zabalí do opravné zprávy (Repair Message), která se vrátí zpět modelu spolu s původním kódem a instrukcí k opravě.

\subsubsection*{Centralizovaná orchestrace a správa stavu}

Pro správu stavu a orchestraci dat byl zvolen přístup založený na kombinaci React hooků a knihovny \texttt{TanStack Query}.
Jelikož aplikace není extrémně komplexní a nevyžaduje složitý state management, nebylo třeba 
využívat mechanismy jako je Redux, které by mohly přinést zbytečnou režii.
Výhodou použití \texttt{TanStack Query} narozdíl od prostých fetch volání je implementovaný systém cachování,
automatické invalidování dat na pozadí a případná synchronizace dat mezi různými komponentami bez 
nutnosti manuálního psaní logiky pro načítání, aktualizaci a správu stavu dat. 
Pro uchování uživatelských nastavení (např. zvolené tooly, které agent smí používat, případně nastavení dark a light režimu) se využívá
prohlížečové úložiště \texttt{localStorage}, 
což umožňuje uchovávání těchto preferencí i mezi jednotlivými relacemi bez nutnosti implementace složitějšího backendového řešení \textbf{(FR-10)}.

\subsection{Real-time streamování a vizualizace procesu}

Při implementaci Server-Sent Events na straně klienta bylo potřeba překonat omezení 
nativního \texttt{EvenSource} API, které podporuje pouze \texttt{GET} požadavky.
Proces generování testů však vyžaduje odeslání objektu s kontextem, k čemuž je nezbytné 
využití metody \texttt{POST}. Streamování je proto implementováno pomocí nízkoúrovňového
 \texttt{fetch} API v kombinaci s \texttt{ReadableStream}.


\subsubsection*{Zpracování streamu a mapování událostí}

\subsubsection*{Řízené přerušení generování (Cancel Path)}

Aby bylo možno bezpečně přerušit probíhající generování testů, je do \texttt{fetch} požadavku injektován 
signál z instance \texttt{AbortController}. Pokud tedy při generování uživatel stiskne tlačítko \textit{Stop} nebo opustí aktuální stránku, 
frontend zavolá metodu \texttt{abort()}, která okamžitě přeruší HTTP spojení s backendem. 
Tento signál je pak na backendu zpracován, což vede k okamžitému zastavení jakékoliv činnosti agenta.

\subsection{Prezentace vygenerovaného kódu a exekuce testů}
Jakmile agent úspěšně dokončí iterativní proces a vygeneruje finální testy, backend odešle událost \texttt{complete}, 
která je zachycena klientskou aplikací. Vygenerovaný kód je následně vizualizován pomocí read-only Monaco editoru, který poskytuje plnohodnotné 
syntaktické zvýrazňování pro jazyk TypeScript, což výrazně zvyšuje jeho čitelnost.
Uživatel má pak možnost tento kód (který se mezitím automaticky uložil i do lokálního souborového systému)
zkopírovat do schránky nebo stáhnout jako \texttt{.spec.ts} soubor. Pokud výsledek neodpovídá představám uživatele,
může vyvolat regeneraci, která automaticky resetuje obsah Activity Feedu a znovu začne vizualizovat nový běh agenta.

Kromě toho může uživatel vygenerované testy i přímo spustit v sekci \texttt{Test Suites} \textbf{(FR-08)}, 
kde je zobrazen přehled všech projektů a jejich asociovaných testů. Frontend v takovém případě 
odešle požadavek pomocí hooku \texttt{useRunTest} na backend, který testy izolovaně spustí. 
Aby bylo možné rozumně zobrazit výsledky testů, byla zvolena možnost generování interaktivního HTML reportu, který je nativně podporován nástrojem Playwright.
Tento report poskytuje detailní informace o průchodu testem, včetně jednotlivých kroků, asercí, chybových hlášek a hlavně 
nabízí i předpřipravený chybový záznam v Markdown formátu, který může uživatel snadno zkopírovat a 
vložit jako feedback pro regeneraci testů. Další ukázky ostatních částí uživatelského rozhraní 
jsou obsaženy v příloze \ref{app:screenshots}.

\section{Shrnutí}
Tato kapitola se věnovala detailnímu popisu implementace celého navrženého systému.

 a vyhodnocení zpětné vazby z uživatelského testování s reálnými uživateli z praxe.

\section{Metodika evaluace LLM agenta a testovací prostředí}
V předchozích univerzitních pracích, které se zabývaly generováním testů pomocí LLM,
se k ověření schopností modelů využíval existující univerzitní systém TBUIS (Testbed University Information System)
\footnote{\href{https://projects.kiv.zcu.cz/tbuis/web/}{Aplikace TBUIS}}.
Tento systém poskytuje sadu use-casů a funkcionalit (např. úmyslné zanešení defektu),
které jsou vhodné pro testování generování testů. Jelikož se v rámci této 
práce vychází z obecných uživatelských příběhů, bylo by potřeba je vytvořit na míru 
pro určitou podmnožinu use-casů v TBUIS.

Proto byla pro účely této práce vyvinuta dedikovaná testovací aplikace, která kopíruje některé
z klíčových funkcionalit TBUIS, ale zároveň umožňuje vlastní rozšíření o další koncepty.
V rámci daného repozitáře se pak rovnou nainstaluje přes NPM balíček nástroj TestPilot AI,
což umožní agenta testovat přímo ve vývojovém prostředí reálné aplikace a zároveň využívá 
jeho schopnost jednoduché integrace do stávajících projektů.



\subsection{Architektura testované aplikace}
Aplikace byla implementována jako monorepo, kde backend byl napsán v Node.js s využitím frameworku Express.js, 
zatímco frontendová část byla vytvořena pomocí Reactu a knihovny komponent Shadcn UI.
Klíčové pro testování schopností LLM agenta bylo záměrné rozhodnutí neimplementovat perzistentní databázi,
ale uchovávat data pouze v paměti Node.js procesu. Díky tomu se při každém spuštění serveru vrací aplikace do přesně definovaného výchozího stavu, 
což je ideální pro testování a v praxi využívané pro E2E testování (např. v rámci CICD pipeline), kde je potřeba mít vždy konzistentní výchozí podmínky.
Aplikace obsahuje několik konceptů, které pomohou ověřit schopnosti LLM agenta detekovat a reagovat na funkční mezery v implementaci - 
např. přístup založený na rolích (admin vs běžný uživatel), dynamické filtry dat nebo transientní UI elementy v podobě Toast notifikací.
Aby bylo možné změřit schopnost agenta detekovat chyby v implementaci, byl do aplikace implementován mechanismus injektování chyb
(\textit{Bug Injection}), který umožňuje úmyslně ``rozbít`` část funkcionality pomocí URL parametru - 
to výrazně ulehčí nastavování testovací aplikace, jelikož není potřeba manuálně spouštět nové verze s různými chybami, 
ale stačí pouze nastavit dedikovaný parametr do URL pro danou chybu.

Během implementace tohoto mechanismu byl identifikován potenciální problém v podobě sémantického úniku (\textit{semantic leakage}). 
Pokud by název parametru a jejich hodnoty nesly lidsky čitelné názvy (např. \texttt{?bug=login\_500}), 
výkonnější modely by mohly chování aplikace detekovat na základě této informace z URL, nikoliv z 
reálného průzkumu uživatelského rozhraní. Aby se tomuto předešlo, byl klíč URL parametru zkrácen na \texttt{?b=} 
a konkrétní typy chyb jsou mapovány výhradně na náhodné alfanumerické hashe. Přehled všech

\subsection{Připravené testovací scénáře}
Pro samotnou evaluaci bylo navrženo 8 komplexních uživatelských příběhů.
Jejich přesné znění je k dispozici v přiloze \ref{app:user-stories}.

Aby bylo možné zhodnotit nejen schopnost modelu generovat kód, ale i schopnost porozumět různě formulovaným akceptačním kritériím a přizpůsobit se jim,
byla akceptační kritéria (AC) záměrně sepsána ve třech odlišných formátech:

\begin{itemize}
    \item \textbf{Deklarativní (Rule-based) styl (US-01 až US-03):} Scénáře popisují pouze výchozí stav a očekávaná 
    pravidla systému. Agent si musí cestu uživatelským rozhraním odvodit zcela sám.
    \item \textbf{Imperativní (Step-by-Step) styl (US-04 až US-06):} Detailní návod specifikující přesné kroky a interakce. 
    Tento formát primárně testuje schopnost modelu striktně následovat instrukce.
    \item \textbf{BDD styl (Given-When-Then) (US-07 a US-08):} Akceptační kritéria jsou zapsané v BDD formátu popsaném v jazyce Gherkin.
\end{itemize}


\section{Výsledky evaluace velkých jazykových modelů}

Aby bylo možné zhodnotit schopnosti navrženého agentního systému TestPilot AI, 
bylo potřeba definovat jasnou metodiku pro generování testů, jejich exekuci a následné hodnocení výsledků.
Cílem této evaluace není pouze posoudit syntaktickou správnost generovaného kódu, ale srovnat výsledky napříč
jednotlivými modely, identifikovat jejich chování napříč scénáři a porovnat efektivitu těchto testů 
s ručně psanými testy.


\subsection{Metodika exekuce a sběru dat}\label{subsection:metodika-exekuce}

Pro zajištění konzistentních výsledků napříč všemi 9 modely byla definována pravidla pro exekuci agenta a 
kategorizaci jeho výstupů. 

\subsubsection*{Agentní exekuce a testované prostředí}
Po úspěšné instalaci NPM balíčku TestPilot AI do testovací aplikace 
byly ručně nahrány do systému veškeré uživatelské příběhy. Jako \texttt{baseUrl} testované
aplikace se použila lokální adresa \texttt{http://localhost:3000}, 
zatímco agentní systém byl pomocí environmentální proměnné \texttt{PORT} nakonfigurován tak, aby běžel na 
adrese \texttt{http://localhost:3002}. 
Nastaveno bylo maximálně 20 iterací (volání nástrojů-API) pro každé generování či regeneraci testu.
To by měl být dostatečný počet na to, aby agent mohl pokrýt všechny požadované kroky v rámci 
daných akceptačních kritérií a zároveň se předešlo nechtěným zacyklením. 

Pro konzistenci a stabilitu výsledků bylo nutné před každým spuštěním generování nového testu
(případně i při regeneraci) manuálně promazat session Playwright prohlížeče a restartovat 
testovací aplikaci. Bez toho kroku docházelo k prolínání stavů (zejména u přihlášení, 
kdy mohla být ještě aktivní sesion z předchozího testu, případně u jiných operací, které vyžadovaly 
operace mazání či editace), což rozporuje 
princip izolace testů a vede k nespolehlivým výsledkům. 

\subsubsection*{Pozitivní scénáře}
V rámci první fáze evaluace agent generoval testy pro fungující aplikaci na základě 8 uživatelských příběhů.
Jelikož cílem bylo i otestování samoopravných schopností agenta, 
byl zaveden limit maximálně jedné povolené regenerace - pokud tedy vygenerovaný test napoprvé selhal,
bylo možné dát agentovi feedback s tím, co selhává (chybová hláška z Playwright reportu) 
a požádat ho o následnou opravu.

Následně bylo potřeba určit metriku, kterou se bude hodnotit kvalita vygenerovaných testů.
Jelikož v rámci end-to-end testování nemáme k dispozici metriky jako je např. 
pokrytí kódu, bylo potřeba zvolit jinou vlastní škálu, která zohlední nejen syntaktickou správnost, 
ale i schopnost testů pokrýt akceptační kritéria a být spustitelné.
Výsledný kód byl hodnocen dle následující čtyřbodové škály:

\begin{itemize}
    \item \textbf{3 (Perfect):} Test prošel úspěšně napoprvé s 
    plným pokrytím akceptačních kritérií bez potřeby regenerace.
    \item \textbf{2 (Regenerated):} Test prošel úspěšně až po využití jednoho dodatečného promptu (regenerace).
    \item \textbf{1 (Partial):} Test byl logicky správně, ale selhal při exekuci (např. kvůli nesprávně zvoleným lokátorům) 
    nebo ignoroval některá akceptační kritéria. Mohl by posloužit jako kostra pro další ladění.
    \item \textbf{0 (Fail):} Kód byl nefunkční, obsahoval chyby a ani po regeneraci nedokázal úspěšně projít scénářem.
\end{itemize}

\subsubsection*{Verifikace defektů}
Druhá fáze evaluace se zaměřila na schopnost modelů detekovat zanesené chyby.
Na rozdíl od první fáze zde byla vynechána jakákoliv dodatečná regenerace,
aby bylo možné zachytit prvotní dedukci modelu při kontaktu s rozbitou aplikací.
Výsledky těchto experimentů byly kategorizovány do tří skupin: 

\begin{itemize}
    \item \textbf{D (Detected):} Model správně detekoval rozdíl mezi zadáním a akceptačními kritérii a 
    defekt identifikoval (např. pomocí \texttt{test.fail()} či záznamu v \texttt{IMPLEMENTATION NOTES}).
    \item \textbf{FN (False Negative):} Kritické selhání - model ignoroval zanešenou chybu 
    a test vyhodnotil jako úspěšný (v \texttt{IMPLEMENTATION NOTES} potvrzuje splnění kritérií, 
    i když ve skutečnosti je funkcionalita rozbitá).
    \item \textbf{E (Error):} Agent napsal test, který nedoběhl (např. volba špatného selektoru) a nebo
    vůbec nevygeneroval sekci \texttt{IMPLEMENTATION NOTES}, kde by měl být zaznamenán zjištěný defekt.
\end{itemize}

\subsubsection*{Kvalita kódu a architektonické rozdíly}
Pokročilejší modely jako \textit{GPT-5} či \textit{Gemini 2.5 Pro} prokázaly 
schopnost vytvářet testy s vysokou mírou abstrakce. Jak je vidět na ukázce \ref{testing:shared-functionality},
v rámci \texttt{US-07} model \textit{GPT-5} vygeneroval funkci \texttt{login}, 
která centralizuje logiku přihlašování a může být znovu použita napříč různými testy.
To poté model aplikoval právě v jednotlivých testech - jednou pro přihlášení za běžného uživatele a podruhé 
pro přihlášení za administrátora.

\begin{lstlisting}[style=tscode, 
    caption={\protect\centering Ukázka sdíleného kódu pro přihlášení vygenerovaného modelem GPT-5.}, 
    label={testing:shared-functionality},
    basicstyle=\ttfamily\scriptsize,
    float=false]

async function login(page: Page, email: string, password: string): Promise<void> {
  await page.goto(baseUrl);
  await page.getByRole('textbox', { name: 'Email' }).fill(email);
  await page.getByRole('textbox', { name: 'Password' }).fill(password);
  await page.getByRole('button', { name: 'Login' }).click();
  await page.waitForURL('**/dashboard');
  await expect(page.getByRole('heading', { name: 'TaskMaster Pro' })).toBeVisible();
}
\end{lstlisting}

Rozdílem je i způsob práce se selektory. Dražší modely často nevkládaly 
hard-coded selektory do každého kroku, ale vytvářely částečnou abstraktní vrstvu nad UI prvky 
- například pomocí deklarace proměnných pro klíčové elementy (např. \texttt{const taskList = page.getByRole("list", \{ name: "Tasks" \});}).
S tím souvisí i synchronizace a práce s asynchronními událostmi - zatímco model \textit{Haiku 3}
využíval explicitně definovaný timeout (\texttt{page.waitForTimeout(500)}), model \textit{GPT-5-mini} 
využil event-driven přístup (\texttt{page.once('dialog')}).

Zajímavý rozdíl se projevil také v rozsahu testovací logiky. Model \textit{Claude Sonnet 4.5} často
rozšiřoval testy nad rámec explicitně definovaných akceptačních kritérií a přidával dodatečné kontroly
např. pro validaci HTML atributů, stavů formulářů nebo alternativních uživatelských cest.
Např. v rámci testu \texttt{US-01} vytvořil kromě 4 test-casů požadovaných akceptačními kritérii 
i další dva:
\begin{itemize}
    \item \textbf{Complete Registration \& Login Flow} - kompletní životní cyklus od první návštěvy,
    přes registraci, přihlášení až po odhlášení. V zásadě kombinuje předchozí 4 test-casy 
    do jednoho komplexního scénáře, který ověřuje nejen jednotlivé kroky, ale i jejich vzájemnou integraci.
    \item \textbf{Edge Cases \& Error Handling} - test ověřující duplicitní registraci se stejným e-mailem a 
    jednoduchý UX test s cílem ověřit, zda se z registračního formuláře na přihlašovací dostaneme i přes 
    prokliknutí na odkaz \texttt{Go to login}.
\end{itemize}

Ostatní modely se striktně držely zadání a implementovaly
pouze minimální sadu kroků nutných k ověření scénáře.

\subsubsection*{Halucinace u modelů nižší třídy}
Modely \textit{Haiku} vykazovaly velmi časté halucinace v API frameworku Playwright.
Typickým příkladem bylo volání neexistujících metod jako \texttt{page.snapshot()} nebo použití
chybných asercí typu \texttt{not.toBeInDOM()} a \texttt{not.toExist()}. 
Tyto modely rovněž často odhadovaly texty tlačítek (např. očekávaly ``Sign In`` místo reálného ``Login``), 
což vedlo k okamžitému selhání exekuce. Při vývoji systému byla snaha těmto 
jevům zamezit, a proto byl do systémového promptu přidán i požadavek na použití vícero 
nástrojů před psaním kódu - viz sekce \textit{MANDATORY WORKFLOW} v příloze \ref{lst:system-prompt-full}.
Přestože modely v rámci generování testů využily některé z dostupných nástrojů,
nebylo to dostatečné k eliminaci těchto halucinací. To bylo viditelné i v rámci 
regenerace, kde v promptu není explicitně vyžadováno, aby se použily nástroje pro validaci chyb, 
ale je pouze uvedeno, že se tyto MCP nástroje mají použít k inspekci stránky. 
\textit{Haiku 3} model pak nevyužil žádné a rovnou se z Thinking procesu 
přesunul k psaní kódu, který byl sice syntakticky správný a prošel validační 
pipeline popsanou v kapitole \ref{chapter:implementation}, 
ale selhal při exekuci kvůli halucinacím v API a selektorech.

\subsubsection*{Přínos regenerační smyčky}
Během evaluace se ukázalo, že samoopravná regenerační smyčka je prvek, který 
výrazně zvyšuje úspěšnost generování testů - z tabulky \ref{tab:happy-path-results} je vidět, 
že celkem 19 testů bylo díky regeneraci opraveno z původního selhání.
Nejčastěji se jednalo o opravy spojené s výběrem selektorů, 
kdy model po obdržení chybové hlášky z Playwright reportu dokázal identifikovat, 
že problémem jsou špatné lokátory a následně (s využitím nástrojů pro inspekci stránky)
vygeneroval opravený test. Došlo i k ojedinělým případům (zejména při práci s Toast notifikacemi),
kdy model nebyl schopen správně synchronizovat test s transientními elementy a 
vyhodnotil funkcionalitu jako nefunkční. V těchto speciálních případech byl
v rámci regeneračního promptu požádán o prověření této funkcionality,
kdy model následně vyřešil problém se synchronizací a test úspěšně opravil (zejména u \texttt{US-04}).

které z nich bylo splněné a které ne. Nefunkční validaci hesel (AC\_02) 
nejen správně označil v rámci této sekce, ale i v samotném testu využil \texttt{test.fail()} 
s jasným popisem očekávaného chování, které však v aplikaci chybí. 
Test dále pokračuje s kroky, které by měly být provedeny a nakonec obsahuje aserce,
které by v případě správné implementace měly být úspěšné.

\subsubsection*{Falešně negativní výsledky}
V rámci detekce defektů se objevily i případy falešně negativních výsledků, zejména u 
modelu \textit{GPT-4o}. Například u chyby \texttt{filter\_broken} model nahlásil úspěšné splnění testu,
přestože byl filtr nefunkční. Po analýze vygenerovaného kódu bylo možné
identifikovat několik příčin, které k tomuto selhání vedly:

\begin{itemize}
    \item Použití příliš obecných asercí (např. \texttt{getByText}),
    které nejsou vázány na konkrétní kontext nebo stav UI.
    
    \item Použití selektorů, které neodpovídají žádnému prvku v DOM stromu.
    V takovém případě test sice formálně proběhne, ale neprovede žádné ověření,
    protože všechny operace probíhají nad prázdným výsledkem.

    \item Absence explicitních negativních kontrol, zejména v případech,
    kdy bylo potřeba ověřit neexistenci prvku nebo chybové hlášky.
\end{itemize}

\subsubsection*{Absence Prompt Cachingu u Anthropic modelů}
Výraznou anomálií v naměřených datech je vysoká nákladnost modelů od Anthropic, zejména \textit{Claude Sonnet 4.5}.
Tento rozdíl je způsoben architekturou použité AI Gateway, skrze kterou byly modely volány.
Modely rodiny GPT a Gemini využívají automatické cachování opakujícího se kontextu,
kde se na straně providera LLM pomocí speciálních prefixů hlaviček identifikují části promptu, 
které se nemění mezi jednotlivými requesty (v rámci TestPilot AI se jedná o historii zpráv a definic nástrojů)
a tyto části se pak cachují, díky čemuž se opakující se kontext nemusí znovu načítat a tokenizovat,
ale pouze se tokenizuje nový obsah (např. příkaz k volání nástrojů). To vede k výraznému 
snížení nákladů na generování testů.

U Anthropic modelů však tento mechanismus neprobíhá automaticky. 
Cachování je nutné implementovat manuálně buď na úrovni AI Gateway, 
nebo přímo v aplikaci pomocí definice tzv. breakpointů.
Jak popisuje oficiální dokumentace platformy Claude\footnote{\href{https://platform.claude.com/docs/en/build-with-claude/prompt-caching\#understanding-cache-breakpoint-costs}
{Dokumentace Claude Prompt Caching}}, využití takto cachovaného tokenu stojí 
pouze 10 \% ceny běžného vstupního tokenu.

Při případné plné implementaci této funkce 
by mohly reálné náklady na model \textit{Sonnet 4.5} klesnout o desítky procent a 
dostat se na úroveň konkurenceschopnou s modelem \textit{GPT-5}, čímž by se tento model stal ještě atraktivnějším 
kandidátem pro nasazení v produkčním prostředí.

\subsection{Porovnání s ručně psanými testy}
Aby bylo možné posoudit skutečný přínos autonomního agenta pro generování testů,
byla pro srovnání vytvořena sada manuálně psaných testů.
Jedná se o 8 pozitivních scénářů (pro každý uživatelský příběh jeden), 
které byly implementovány ručně pomocí oficiálního nahrávacího nástroje Playwright (\textit{Codegen}).
Ten je integrován jako rozšíření (\textit{Extension}) ve vývojovém prostředí Visual Studio Code 
a umožňuje generování kódu na základě interakcí uživatele s aplikací bez hlubší znalosti programování, což
dokonale odpovídá cílové skupině uživatelů, kteří by mohli využívat autonomního agenta pro generování testů.
Vytvoření těchto testů zabralo přibližně 2 hodiny včetně manuálního doplňování asercí.

\subsubsection*{Limity nahrávacích nástrojů}
Přestože nástroj \textit{Codegen} výrazně urychluje prvotní psaní kostry testů tím, 
že překládá akce uživatele (kliknutí, vyplňování textu, navigace) do kódu,
ukázalo se, že tento přístup má několik zásadních omezení.
Poskytuje pouze základní záznam interakcí, ale nedokáže popsat a zachytit komplexnější logiku 
- tu je poté třeba nutné doplňovat ručně, což vyžaduje už alespoň základní znalost programování.

Ukázkovým příkladem je ověření klientské validace formuláře u scénáře \texttt{US-02}.
Záznamový nástroj nedokáže zachytit nativní varovnou bublinu prohlížeče (``Vyplňte toto pole``), 
protože se nejedná o standardní DOM element. Jak je vidět na ukázce \ref{testing:manual-vs-ai}, 
při ručně nahraném testu bylo nutné manuálně doplnit dodatečnou aserci.
Naopak modely jako \textit{GPT-5} či \textit{Claude Sonnet 4.5} 
volí sofistikovanější přístup - nemusí nic nahrávat a doplňovat. Místo toho rovnou 
syntetizují kód, a pracují na úrovni vnitřního stavu HTML elementu, nikoliv na úrovni vizuálního zobrazení.

\begin{lstlisting}[style=tscode,
    caption={\protect\centering Porovnání manuálního řešení a přístupu modelu GPT-5 při ověřování nativní validace formuláře.},
    label={testing:manual-vs-ai},
    basicstyle=\ttfamily\scriptsize,
    float=false]
// 1. Implementation with Playwright Codegen
await page.getByRole('button', { name: 'Login' }).click();
// Manual workaround - this is a limitation of the recording tool, 
// which cannot capture native browser validation bubbles.
await expect(page.locator("input:invalid")).toHaveCount(1);

// 2. TestPilot AI implementation (model GPT-5)
await loginButton.click();
const titleValidity = await titleInput.evaluate((el: HTMLInputElement) => ({
    valid: el.checkValidity(),
    valueMissing: el.validity.valueMissing,
    required: el.required === true || el.getAttribute("required") !== null
}));
expect(titleValidity.required).toBe(true);
expect(titleValidity.valid).toBe(false);
expect(titleValidity.valueMissing).toBe(true);
\end{lstlisting}


Dalším omezením manuálního nahrávání byla logická neschopnost ověřit neexistenci
elementu. Například ve scénáři \texttt{US-03} běžný uživatel nesmí vidět 
administrátorské menu. Codegen nemůže zaznamenat kliknutí na něco, co na obrazovce fyzicky není.
Bylo proto nutné dopsat ručně manuální aserci (\texttt{not.toBeVisible()}) pro ověření, že tento prvek není přítomný.
Naopak modely rovnou pochopily požadavek a automaticky generovaly 
aserce na absenci daného prvku v DOM stromu (např. pomocí \texttt{toHaveCount(0)}).

\subsubsection*{Časová efektivita}

Zatímco manuální vytváření testů pomocí Codegenu a následného ručního doplňování asercí zabralo 
přibližně 15 minut pro každý scénář, agent dokázal vygenerovat robustnější test v řádu 
nižších jednotek minut (zpravidla 2-5 minut v závislosti na komplexitě scénáře, modelu a případné regeneraci).
To nastiňuje, že případná integrace autonomního agenta do QA by 
mohla přinést nejen značnou časovou úsporu, ale mohla by i zlepšit kvalitu 
testů právě díky eliminaci problémů spojených s manuálním nahráváním.



\section{Testování softwarové implementace nástroje}

Před uživatelskými testy bylo potřeba zajistit stabilitu a spolehlivost systému TestPilot AI.
Vzhledem k tomu, že obsahuje jak frontendovou část pro interakci s uživatelem, tak i backendovou část pro orchestraci 
a komunikaci s LLM, bylo nezbytné pokrýt testy obě tyto části.

\subsection*{Testování backendové části}
Pro testování backendové části byl využit framework Jest v kombinaci s knihovnou Supertest 
pro end-to-end testování API endpointů.
Důraz byl kladen na otestování klíčové business logiky, která zajišťuje orchestraci mezi jednotlivými komponentami systému,
jakož i na správné fungování API endpointů, které jsou kritické pro komunikaci mezi frontendem a backendem.
Hlavní oblasti, které byly testovány, zahrnovaly:

\begin{itemize}
    \item \textbf{Services:} Nejvyšší pokrytí pro klíčové služby 
    zajišťující orchestraci (např. \texttt{LlmService}, \texttt{AgentService}, \texttt{TestRunnerService}).
    \item \textbf{Controllers:} Ověřování zpracování HTTP požadavků a správné volání služeb.
    \item \textbf{Konfigurace a validace:} Testování parserů a validačních Zod schémat pro nástroje agenta.
\end{itemize}

Testovací sada obsahuje celkem 320 jednotkových a integračních testů rozdělených do 
31 testovacích sad. Line coverage dosahuje přibližně 82~\% a function coverage téměř 90~\%.

\subsection*{Testování frontendové části}
V rámci klientského testování je použit framework Vitest, který 
je optimalizován pro rychlé testování v prostředí Vite.
Simulace uživatelských interakcí a testování komponent probíhá prostřednictvím React Testing Library
za pomoci JSDOM.
Testy se zaměřují především na ověření správného renderování a reprezentace stavu u klíčových komponent, 
a dále také na funkčnost hooků, které obsahují oddělenou logiku pro správu stavů a interakcí.
Celkem klientská část čítá 159 testů a 
pokrytí se pohybuje okolo 60~\%. 

\section{Uživatelské testování a zpětná vazba}
Pro ověření praktické použitelnosti nástroje TestPilot AI bylo 
provedeno uživatelské testování prostřednictvím dotazníku 
v Google Forms, který obsahoval otázky zaměřené na různé aspekty nástroje 
a otevřenou sekci pro volné komentáře a návrhy na zlepšení.
Dotazník byl vyplněn 4 respondenty z firmy Emplifi (dvěma architekty, jedním SW inženýrem a jedním QA inženýrem), 
jejichž kompletní odpovědi jsou uvedené v příloze \ref{app:userTesting}.

\subsection*{Hodnocení klíčových aspektů a celkový dojem}
Odpovědi respondentů indikují spokojenost s nástrojem a jeho přínosem pro vývojový proces:

\begin{itemize}
    \item \textbf{Inicializace a integrace:} Každý respondent ohodnotil proces 
    počátečního nastavení pomocí příkazu \texttt{npx testpilot init/run} nejvyšší možnou známkou 
    (5/5 - Velmi snadné). Pozitivně (5/5) bylo hodnoceno i lokální ukládání testů přímo do 
    repozitáře namísto využití interní databáze.
    \item \textbf{Kvalita kódu a asistentce:} Shoda vygenerovaného kódu s akceptačními kritérii i 
    dodržování Playwright best-practices byly hodnoceny poměrně kladně (převážně 4/5). 
    \item \textbf{Časová úspora a celkový dojem:} Všichni 4 respondenti se shodli (možnost ``Určitě ano``), 
    že nástroj má potenciál šetřit čas při psaní boilerplate kódu pro E2E testy. Celková známka nástroje dosáhla 
    průměrné hodnoty 1,25 (na škále 1 = Vynikající, 5 = Nepoužitelný) a 100 \% testujících vidí v 
    tomto prototypu potenciál, který by po dalším vývoji mohl být plnhodnotně využitelný ve vývojovém procesu.
\end{itemize}

\subsection*{Silné stránky a přínosy}
V otevřených odpovědích respondenti vyzdvihovali 
transparentnost celého procesu. Zobrazování myšlenkových pochodů agenta a volání konkrétních
nástrojů bylo hodnoceno jako přínosné a užitečné pro pochopení toho, jak model dospěl k danému kódu.
Silnou stránkou, kterou zmiňovali zejména architekti, byla snadná integrace do existujících projektů.
Jeden z respondentů dokonce uvedl, že tato jednoduchost otevírá cestu k tvorbě automatizovaných testů 
i pro méně technické role ve firmě, což by plně odpovídalo původnímu záměru nástroje - 
umožnit psaní testů i uživatelům bez hlubších technických znalostí.
Kladně byla hodnocena i schopnost modelů regenerovat testy - 
jeden z respondentů explicitně uvedl, že pokud zadání obsahovalo nejednoznačnosti, 
oprava na základě chybového reportu byla zpravidla úspěšná již na první pokus.

\subsection*{Identifikované limity a návrhy na zlepšení}
Zpětná vazba od uživatelů byla i cenná pro identifikaci oblastí, které by bylo možné v budoucnu vylepšit.
Zmiňováno bylo:

\begin{itemize}
    \item \textbf{Izolace testovacího prostředí:} QA inženýr narazil na problém se 
    sdíleným stavem prohlížeče (pokud byl uživatel již přihlášen z předchozí interakce, agent selhal, protože nenašel 
    přihlašovací formulář). Tento poznatek se plně shoduje se zjištěními z této kapitoly, 
    kde byla nutnost manuálního čištění session definována jako jeden z limitů.
    \item \textbf{Úprava existujících testů:} Dva respondenti uvedli, že pro 
    plné nahrazení současných nástrojů jim chybí možnost nechat agenta upravovat již existující
     testy, nikoliv pouze generovat testy nové nebo regenerovat ty čerstvě vytvořené.
    \item \textbf{Uživatelské rozhraní:} Byla identifikována drobná UX nedokonalost u tlačítka pro
     regeneraci, které vizuálně neindikuje, že otevře modální okno pro dodatečný kontext, a působí spíše 
     jako tlačítko pro okamžitou exekuci. Dále byla zmíněna absence persistence stavu při přepínání mezi 
     záložkami jednotlivých uživatelských příběhů.
    \item \textbf{Paralelní generování testů:} Jeden z respondentů navrhl možnost spouštět generování testů 
    pro více uživatelských příběhů paralelně, což by mohlo výrazně zrychlit celý proces, zejména v případech, 
    kdy je potřeba vytvořit testy pro větší množství scénářů.
\end{itemize}

Lze konstatovat, že uživatelské testování potvrdilo nejen praktickou použitelnost nástroje, 
ale i jeho potenciál pro zrychlení vývojového cyklu a umožnění psaní testů i pro méně technické role.
Zároveň poskytlo cenné poznatky pro další vývoj a vylepšení, které by mohly tento nástroj 
učinit ještě efektivnějším a uživatelsky přívětivějším.

V rámci této kapitoly byla provedena důkladná evaluace agentního systému,

automatizovaného E2E testování. Analýza výsledků ukázala, 
že pokročilé reasoning modely dokáží nejen generovat funkční testy, 
ale především i detekovat chyby v implementaci, což je klíčová schopnost pro praktické využití v QA procesech.
Navíc srovnání s manuálně psanými testy ukázalo, 
že agentní systém eliminuje limity běžně využívaných nahrávacích nástrojů a zkracuje 
dobu potřebnou pro vytvoření testu. Ekonomické zhodnocení pak poukázalo na existenci

Pro ověření stability nástroje byly napsány i automatizované testy pro backend i frontend,

zlepšení. Tím se bude zabývat následující kapitola, která se zaměří na možná vylepšení a

\chapter{Možná vylepšení}\label{chapter:improvements}

Přestože evaluace výsledných vygenerovaných testů a uživatelské testování

současná Proof of Concept implementace obsahuje prostor pro další rozvoj a zlepšení.
Na základě zjištěných technických limitů a cenné zpětné vazby od respondentů bylo

\section{Správa testů a jejich úpravy}
Jak vyplynulo z uživatelského testování, pro reálné nasazení v agilním vývoji nestačí testy pouze jednorázově generovat.
Systémy, pro něž jsou testy generovány, se neustále vyvíjejí a s tím přichází i potřeba průběžné údržby testů, aby zůstaly relevantní a funkční.
Významným vylepšením by proto byla podpora pro autonomní údržbu již existujících testů. Agent by dokázal načíst již existující kód testu,
správně ho propojit a porovnat s novými verzemi akceptačních kritérií nebo aktuálním stavem DOM stromu 
a následně navrhnout nezbytné úpravy. To by pomohlo QA inženýrům udržovat 
aktuální testovací sady bez nutnosti manuálního zásahu do kódu, 
čímž by se i snížila celková časová náročnost na údržbu testů a 
umožnilo by to rychlejší adaptaci na změny v aplikaci.
Tento proces by pouze daný test přepsal v rámci daného repozitáře, 
takže by se zachovala historie změn a bylo by možné kdykoliv revertovat zpět k předchozí verzi testu.


\section{Automatizovaná izolace prostředí}
Jedním z hlavních omezení identifikovaných během testování 
byl problém se sdíleným stavem prohlížeče mezi jednotlivými iteracemi generování testů. 
Tento problém se projevoval zejména tím, že agent pracoval s perzistentní instancí prohlížeče, ve které 
zůstával zachován stav z předchozích kroků (např. zmiňované aktivní přihlášení).
V důsledku toho byly následně generované nebo upravované testy ovlivněny již modifikovaným stavem aplikace, což 
bylo potřeba vyřešit manuálním resetováním stavu prohlížeče před každou iterací generování testu.
To je ale zdlouhavé a neefektivní.

Dalším rozšířením nástroje by mohlo být zavedení mechanismů pro automatickou izolaci testovacího prostředí
mezi jednotlivými generacemi testů. 
Toho by mohlo být implementováno několika způsoby, například:

\begin{itemize}
    \item \textbf{Obnova kontextu prohlížeče:} Vytvoření nového browser 
    contextu před každou iterací generování testu, čímž je zajištěno čisté a nezávislé prostředí bez sdíleného stavu.
    \item \textbf{Automatizovaný setup a teardown:} Agent by automaticky prováděl setup a teardown pro každý test, 
    což by zahrnovalo například odhlášení uživatele, vymazání cookies či celého místního úložiště (\texttt{localStorage}).
\end{itemize}

\section{Optimalizace uživatelské přívětivosti a výkonu}
S rostoucím počtem testovaných aplikací (a k ním příslušných uživatelských příběhů) 
se zvyšuje i počet generovaných testů, což může vést k výraznému prodloužení 
doby potřebné pro vygenerování kompletní testovací sady.
Architektura systémy by mohla být rozšířena o následující optimalizace:
\begin{itemize}
    \item \textbf{Paralelní generování testů:} Umožnění běhu více instancí agenta současně nad různými 
    scénáři, díky čemuž by se zkrátil čas pro vygenerovaní kompletní sady testů pro velké množství scénářů. 
    \item \textbf{Streamování odpovědí z LLM:} Současní řešení využívá tzv. \textit{Chat Completion API} přístup - 
    model zpracuje celý požadavek a až poté vrátí kompletní odpověď, která se následně zpracuje na backendu a vrátí uživateli do UI.
    Přechod na stremování odpovědí (\textit{Responses API}) by umožnil sledovat generovaný kód a průběh myšlenkových pochodů v
    reálném čase, což by působilo uživatelsky přívětivějším dojmem a umožnilo i potenciální dřívější detekci případných problémů. 
\end{itemize}

\section{Integrace do firemních ekosystémů}
Pro automizované testování je klíčové i snadné napojení do stávajících 
firemních procesů a nástrojů. Místo ručního vkládání projektů a uživatelských příběhů 
by agent mohl být agent rozšířen o přímou integraci s ALM nástroji - 
konkrétně třeba o Jiru (uživatelské příběhy) a populární plugin Zephyr (správa testovacích případů).
To by umožnilo:

\begin{itemize}
    \item Automaticky stahovat a aktualizovat uživatelské příběhy prostřednictvím Jira API.
    \item Párovat vygenerované testy s testovacími případy v Zephyru, což by vedlo k lepší organizaci a sledovatelnosti testů.
    \item Při opakovaných selháních testů (např. v rámci spouštění Release Candidate buildů) 
    umožnit založení bugu s přiloženým logem - případně i důvodem a návrhem na opravu kódu.
\end{itemize}


\section{Bezpečnostní mechanismy a rozšiřitelnost nástrojů}
Posledním navrhovaným potenciálním vylepšením je zavedení 
bezpečnostních machanismů a rozšíření možností nástrojů, které má agent k dispozici.
Při exekuci E2E testů nad reálnou aplikací může agent teoreticky provést nenávratné operace 
(např. smazání produkčních dat), což by mohlo mít závažné důsledky.
Toto potenciální riziko by mohlo být minimalizováno zavedením konceptu Human-in-the-Loop 
- ten by definoval citlivé akce, které by před svým vykonáním vyžadovaly uživatelův 
explicitní souhlas (např. prostřednictvím modálního okna s možnostmi ``Approve/Reject``).

Zároveň by agent mohl být obohacen i o dodatečné vlastní nástroje. Vývojáři by mohli 
agentovi poskytnout specifické nástroje - např. přímé dotazy do testovacích databází 
či generování testovacích dat, což by umožnilo psát komplexnější scénáře bez nutnosti 
manuálního zásahu do kódu. Díky podpoře Playwrightu (viz kapitola \ref{chapter:therotical_part})

rozšířilo možnost využití nástroje i mimo TypeScriptové projekty.

\section{Systémový prompt}

Tento prompt je využíván pro prvotní generování testů. Instruuje model k provedení
 průzkumu pomocí nástrojů, definuje formát výstupu a pravidla pro křížové ověření zadání s realitou.

\begin{lstlisting}[

  caption={\protect\centering Plné znění systémového promptu s vyznačenými dynamickými bloky.},

You are Test Pilot AI, a Senior QA Automation Engineer specialized in Playwright and TypeScript. Your goal is to generate robust, maintainable e2e tests based on user stories.

## PROJECT CONTEXT
- **Project Name**: ${project.name}
- **Base URL**: ${project.baseUrl}
- **Description**: ${project.description}

Use the Base URL as the starting point for navigation, unless a specific URL is mentioned in the user story.

## USER STORY
**Title**: ${userStory.title}

**Description**:
${userStory.description}

**Acceptance Criteria**:
${userStory.acceptanceCriteria}

**Specification**:
${userStory.extraInfo}

Parse the acceptance criteria carefully - each criterion should map to one or more assertions. Cover both happy path and error/edge cases described.

## MANDATORY WORKFLOW

You have access to Playwright MCP tools. You MUST use them before writing test code - multiple tool calls are required.

### Step 1: NAVIGATE & EXPLORE
- Navigate to the Base URL using browser tools.
- Inspect the page (snapshot, accessibility tree) to understand its structure.
- Identify key UI elements, navigation, and layout.

### Step 2: INTERACT & DISCOVER
- Click through relevant pages/sections described in the user story.
- Inspect forms, buttons, links, modals - find their actual selectors.
- DO NOT assume any selector or element exists without verifying via a tool call.

### Step 2.5: VERIFY AGAINST ACCEPTANCE CRITERIA
Before writing any code, cross-reference each acceptance criterion against what you actually observed:
- For each criterion, determine: does the live application support this behavior?
- Watch for signs of a broken or missing implementation:
  - HTTP error pages (404, 500, "Not Found", "Internal Server Error")
  - Blank or empty pages where content is expected
  - Buttons/forms/elements described in the criteria that do not exist on the page
  - Actions (click, submit) that produce unexpected results (error toasts, no navigation, console errors)
- If a criterion CANNOT be verified because the implementation appears broken or missing, do NOT write a test that asserts against the broken behavior. Instead, write the test with the EXPECTED correct behavior and wrap it with test.fail() plus a comment explaining why it is expected to fail. This way the test still runs, and if the implementation is later fixed, Playwright will report it as an unexpected pass.
- Still generate normal tests for criteria that DO work correctly.

### Step 3: PLAN & CODE
- Based on verified observations, map each acceptance criterion to specific assertions.
- Write test code using ONLY selectors you have actually observed.

## TOOL FAILURE HANDLING
When a tool call returns an error:
1. Acknowledge the failure and the error message.
2. Never pretend the tool succeeded - the result is invalid.
3. Try alternatives: different tool, corrected parameters, different selector.
4. If all attempts fail, report the issue clearly. Do NOT generate code that relies on unverified assumptions.

**Recognizing broken implementations:**
- If navigating to a page returns an error page (404, 500, blank), the feature is likely not implemented or is broken - flag it with test.fail().
- If a UI element described in the acceptance criteria cannot be found after thorough exploration, flag it as a potential implementation gap.
- If an action (click, form submit) produces an unexpected result that contradicts the acceptance criteria, note the discrepancy rather than asserting against the broken behavior.

## SELECTOR STRATEGY
Prefer (in order):
1. Built-in locators: `getByRole`, `getByText`, `getByLabel`, `getByPlaceholder`
2. Data attributes: `page.locator('[data-testid="..."]')`
3. Avoid fragile CSS selectors or XPaths unless necessary

## CODE REQUIREMENTS
- Use TypeScript with proper type annotations
- Store Base URL in a `baseUrl` constant
- Wrap tests in `test('description', async ({ page }) => { ... })`
- Always include assertions - a test without `expect()` is invalid
- Use explicit waits (`waitForSelector`, `waitForLoadState`) over arbitrary timeouts
- Group related tests using `test.describe`
- Pattern: `test('should [expected behavior] when [action/condition]', ...)`

## EXAMPLE OUTPUT
```typescript
import { test, expect } from '@playwright/test';

const baseUrl = 'https://example.com';

test.describe('Login Feature', () => {
  test('should display error message when credentials are invalid', async ({ page }) => {
    await page.goto(baseUrl + '/login');
    await page.getByLabel('Email').fill('invalid@test.com');
    await page.getByLabel('Password').fill('wrongpassword');
    await page.getByRole('button', { name: 'Sign in' }).click();
    
    await expect(page.getByText('Invalid credentials')).toBeVisible();
  });

  test('should redirect to dashboard when login succeeds', async ({ page }) => {
    await page.goto(baseUrl + '/login');
    await page.getByLabel('Email').fill('user@test.com');
    await page.getByLabel('Password').fill('correctpassword');
    await page.getByRole('button', { name: 'Sign in' }).click();
    
    await page.waitForURL('**/dashboard');
    await expect(page.getByRole('heading', { name: 'Dashboard' })).toBeVisible();
  });
});
```

## FINAL OUTPUT
- Return executable Playwright TypeScript test code only.
- Wrap the code in a single ```typescript block.
- The code must be syntactically valid with no undefined variables or missing imports.
- If any acceptance criteria could NOT be verified against the live application, include an IMPLEMENTATION NOTES block at the top of the file summarizing what worked and what did not:

```
/**
 * IMPLEMENTATION NOTES:
 * - [PASS] Criterion that was verified and works correctly
 * - [FAIL] Criterion - expected X, observed Y (possible implementation bug)
 */
```

For criteria flagged as FAIL, write the test with the EXPECTED correct assertions and add `test.fail()` at the start of the test body. This ensures the test still runs (catching future fixes) but Playwright treats the failure as expected rather than a false pass.
